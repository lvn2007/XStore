- [ ] `[XL]` **Improve on "raw Protobuf straight into a fixed slot" — full compression architecture.** Two hard invariants constrain every option below: (a) **arithmetic row addressing** (`offset(t) = (t − FirstEpoch(Y)) × rowLength`) breaks if rows become variable-length inline, so compression must happen at file/frame granularity, never per-row; (b) **skip-parse column extraction** (aggregates decode only the target column via a wire-tag walk over raw mmap'd bytes, ~40-54% faster than full-row decode) breaks if a single column read requires decompressing a whole row — so compression must sit *above* the row, never force full-row decompression to read one column. Three phases:

  **Phase 1 — network wire compression (do first, lowest risk, real bandwidth/latency win).** Compress only the bulk multi-row payloads: `BatchInsert_REQ`, `RangeInsert_REQ`, and the streamed chunk frames of `BatchQuery_REP`/`RangeQuery_REP`. Skip Unary ops entirely — a single row is tens of bytes, ZMQ/TCP framing overhead already dominates, compression call overhead would net-lose latency. Codec: **zstd**, not LZ4 — one dependency instead of two, zstd's negative "fast" compression levels (-1 to -5) match LZ4-class throughput/latency while still beating LZ4's ratio on structured protobuf bytes, and zstd unlocks trained dictionaries for Phase 2 without a second library. `libzstd-dev` is already an apt dependency in CI (`.gitlab-ci.yml`) but currently unused — wire it into CMake via `find_package(zstd)`. Wire format per frame: `[u8 codec: 0=raw,1=zstd][u32 uncompressed_len][payload]` — compress, compare sizes, fall back to raw if compression didn't help (skip the attempt below ~2-4KB, where header+frame overhead isn't worth it). No negotiation needed since client and server are versioned together in this repo. Touch points: new `include/XStore/XStore_Compression.h`/`src/XStore/XStore_Compression.cpp` (`CompressFrame`/`DecompressFrame`), `src/XStore_Networking/ZMQ_Server.cpp` (wrap the streamed chunk sends and the two bulk-insert request parses), `client_src/Cpp/XStore_Client.h` (mirror on the client), `client_src/Python/XStore.py` (same, via the `zstandard` package), both `CMakeLists.txt` files (link zstd). Verification: round-trip unit tests (empty/tiny-below-threshold/large-compressible/large-incompressible), extend `XStoreZmqNetworkTest.cpp`, before/after `xstore_perf_tests` numbers on `BatchInsert`/`BatchQuery`/`RangeInsert`/`RangeQuery` throughput+latency.

  **Phase 2 — cold storage compression (after Phase 1, real disk-footprint win).** Once a `.XSTORE` year file is no longer the current calendar year, it's write-cold. Compress it whole-file with zstd at a high level (15-19, since this is a rare background op) plus a **trained dictionary** (`ZDICT_trainFromBuffer` on a sample of that DB's rows) — small individual protobuf rows don't compress well alone, but share massive structural redundancy (field tags, dtypes, magnitude ranges) a trained dictionary captures well. A background compaction thread (sibling to the WAL writer/data-fsync-coalescer threads) compresses old year files to `<YEAR>.XSTORE.zst` and removes the raw file once verified. Read path: on first access to a compressed year, decompress into a scratch cache file, mmap that exactly as today — **zero changes to `XStore_IO.cpp` scan/skip-parse/aggregate kernels**, since the decompressed scratch file is byte-identical to today's raw format. LRU-cap resident decompressed years (2-3), evict by deleting the regenerable scratch copy. Mutation to a cold year (rare deletes/backfill): decompress to scratch if not already, apply via existing mutate code unchanged, mark dirty, recompress on the next compaction pass.

  **Phase 3 — columnar dtype-specific encoding (optional, highest ratio, highest effort).** Only worth pursuing if Phase 2's generic zstd+dictionary ratio proves insufficient. For maximum ratio on numeric time-series columns specifically: delta/delta-of-delta encoding for timestamps, Gorilla-style XOR encoding for doubles/floats (as used by Facebook Beringei, Prometheus, InfluxDB), frame-of-reference + bit-packing for integers (ClickHouse/Parquet-style), dictionary/RLE for repeated categorical strings, generic zstd fallback for bytes. Requires transposing a row-group (N consecutive rows within a year file) into per-column arrays at compaction time, encoding each column with its dtype-appropriate scheme, then zstd-compressing the result — a real structural addition (a columnar side-format for cold data only; the live/hot format stays row-oriented protobuf for the addressing/skip-parse reasons above).
  - **Status (2026-10-08):** Three phases: wire compression, cold-storage compression, columnar encoding.

Explicitly **not** a replacement for `rowLength`-based enforcement — that enforcement is what guarantees XStore's core fixed-width arithmetic addressing invariant (`offset(t) = (t − FirstEpoch(Y)) × rowLength`), which requires every row to be exactly the same byte size. A variable-width column would still need its own declared max size (truncated/padded to fit) for this to work at all, meaning `rowLength` (or its exact equivalent) stays the real invariant underneath; typed-schema declaration would just be sugar that *derives* it automatically for the fixed-numeric-type case, not a structural replacement. ## 3. Won't do / intentional (no action unless a real need appears)

- ~~**Make `AnyFenced()` per-DB / per-file**~~ — **won't do for now (owner decision 2026-10-10).** It stays process-wide: while any WAL file is fenced (a failed replay at startup, cleared by a later successful replay of that file or by a restart), large records of every DB lose the direct path (records up to half the ring go through the ring; larger ones fail "overloaded" after the stall timeout). Documented in the Technical Reference. A per-file version needs replay to record the data files a failed shard touched, and would not help for failures early in replay (stat/open/read error) where nothing is known. Revisit if fenced shards show up in a real deployment.

- ~~**Lower the streamed-query memory ceiling**~~ — **won't do (2026-09-26).** The 64 MiB `STREAMED_QUERY_CHUNK_SIZE_BYTES` was chosen by a recorded sweep (`XStore_Tunables.h:527-540`: flat latency across sizes, low frame count for real networks, RSS within ~4% of the 8 MB end). Lowering it trades real-network performance for a small transient-memory gain.

- ~~**Cap the ZMQ send queue for streamed replies**~~ — **won't do (2026-09-26).** A bounded HWM would make a server worker wait on slow clients (and, with the read lock held during `emit_chunk`, stall writers on that range) to guard a backlog never observed locally. Revisit only if slow remote clients pulling huge results become a real deployment.

- ~~**Sync-error classification for data-file fsync**~~ — **won't do (owner decision 2026-10-09).** Leave data-file fsync without an errno allowlist (the EINVAL/ENOTSUP/EOPNOTSUPP/EROFS allowlist stays directory-fsync only). Believed theoretical: data syncs use a throwaway fd by path (kernel errseq: an error already reported to another descriptor is not reported again; the startup index rebuild also `fdatasync`s data files). Revisit only if a real filesystem is seen failing there.

- [x] *(Not a bug, documented as intentional; re-confirmed against the code and closed by the owner 2026-10-20)* **2GB response-size reject on Batch/RangeQuery.** Confirmed: the existing 64MB chunk streaming (`XStore_WireEncode.h`) only bounds server-side RAM for large-but-under-2GB replies; it does not and cannot lift the ceiling, because the client reassembles all chunks into one buffer before a single `ParseFromArray` (`XStore_Client.h:97-129`) — a >2GB result would corrupt on the client regardless of server-side streaming. The check runs before any chunk is sent, against the total requested size. No pagination/cursor mechanism exists to fetch a >2GB result across multiple round trips. The code's own comments already document this as intentional.

- ~~**Raise the default worker count above one per logical core**~~ — **no change (measured 2026-10-27).** What caps 20-row SYNC at ~4K calls/s is the 32-worker pool, not CPU, network or the clients: each SYNC call holds a worker for the whole WAL commit, so workers / ~7.5 ms per call = ~4.2K/s. With 128 client threads the rate scales with `-t`: 16/32/48/64/96 workers = 2.6K/4.1K/5.5K/7.0K/9.2K calls/s (spreads under 5%). Other workloads: 32 client threads, bulk SYNC, range and batch queries unchanged (batch p99 +50% at 64+); inserts next to light queries best at 48 (+29% inserts, +44% queries), worse at 96; inserts next to CPU-saturating queries WORSE at 48 (inserts 0.82x, queries 0.84x, query p99 +60%). A fixed higher default would trade one for the other, so it stays at the logical core count; `-t 64` or higher is the knob for SYNC-heavy deployments with light queries (Tech Reference section 5.2). Revisit if a real workload mix is known. Not tested: other hardware, 256+ client threads (a 128-worker run at 128 client threads was slower than 64, cause not investigated).
