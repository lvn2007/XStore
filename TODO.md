Explicitly **not** a replacement for `rowLength`-based enforcement — that enforcement is what guarantees XStore's core fixed-width arithmetic addressing invariant (`offset(t) = (t − FirstEpoch(Y)) × rowLength`), which requires every row to be exactly the same byte size. Column-count alone can only stand in for that guarantee when every column is a fixed-size type; the moment a variable-width type (string/bytes) is allowed in a column — which XStore already supports and tests today via the `oneof`-per-field design — two rows with identical column counts can have wildly different serialized sizes, breaking fixed-width addressing. A variable-width column would still need its own declared max size (truncated/padded to fit) for this to work at all, meaning `rowLength` (or its exact equivalent) stays the real invariant underneath; typed-schema declaration would just be sugar that *derives* it automatically for the fixed-numeric-type case, not a structural replacement. Own future brainstorm/design cycle — not bundled into the variance/stddev work that surfaced it.

- [ ] **Improve on "raw Protobuf straight into a fixed slot" — full compression architecture.** Two hard invariants constrain every option below: (a) **arithmetic row addressing** (`offset(t) = (t − FirstEpoch(Y)) × rowLength`) breaks if rows become variable-length inline, so compression must happen at file/frame granularity, never per-row; (b) **skip-parse column extraction** (aggregates decode only the target column via a wire-tag walk over raw mmap'd bytes, ~40-54% faster than full-row decode) breaks if a single column read requires decompressing a whole row — so compression must sit *above* the row, never force full-row decompression to read one column. Three phases:

  **Phase 1 — network wire compression (do first, lowest risk, real bandwidth/latency win).** Compress only the bulk multi-row payloads: `BatchInsert_REQ`, `RangeInsert_REQ`, and the streamed chunk frames of `BatchQuery_REP`/`RangeQuery_REP`. Skip Unary ops entirely — a single row is tens of bytes, ZMQ/TCP framing overhead already dominates, compression call overhead would net-lose latency. Codec: **zstd**, not LZ4 — one dependency instead of two, zstd's negative "fast" compression levels (-1 to -5) match LZ4-class throughput/latency while still beating LZ4's ratio on structured protobuf bytes, and zstd unlocks trained dictionaries for Phase 2 without a second library. `libzstd-dev` is already an apt dependency in CI (`.gitlab-ci.yml`) but currently unused — wire it into CMake via `find_package(zstd)`. Wire format per frame: `[u8 codec: 0=raw,1=zstd][u32 uncompressed_len][payload]` — compress, compare sizes, fall back to raw if compression didn't help (skip the attempt below ~2-4KB, where header+frame overhead isn't worth it). No negotiation needed since client and server are versioned together in this repo. Touch points: new `include/XStore/XStore_Compression.h`/`src/XStore/XStore_Compression.cpp` (`CompressFrame`/`DecompressFrame`), `src/XStore_Networking/ZMQ_Server.cpp` (wrap the streamed chunk sends and the two bulk-insert request parses), `client_src/Cpp/XStore_Client.h` (mirror on the client), `client_src/Python/XStore.py` (same, via the `zstandard` package), both `CMakeLists.txt` files (link zstd). Verification: round-trip unit tests (empty/tiny-below-threshold/large-compressible/large-incompressible), extend `XStoreZmqNetworkTest.cpp`, before/after `xstore_perf_tests` numbers on `BatchInsert`/`BatchQuery`/`RangeInsert`/`RangeQuery` throughput+latency.

  **Phase 2 — cold storage compression (after Phase 1, real disk-footprint win).** Once a `.XSTORE` year file is no longer the current calendar year, it's write-cold. Compress it whole-file with zstd at a high level (15-19, since this is a rare background op) plus a **trained dictionary** (`ZDICT_trainFromBuffer` on a sample of that DB's rows) — small individual protobuf rows don't compress well alone, but share massive structural redundancy (field tags, dtypes, magnitude ranges) a trained dictionary captures well. A background compaction thread (sibling to the WAL writer/data-fsync-coalescer threads) compresses old year files to `<YEAR>.XSTORE.zst` and removes the raw file once verified. Read path: on first access to a compressed year, decompress into a scratch cache file, mmap that exactly as today — **zero changes to `XStore_IO.cpp` scan/skip-parse/aggregate kernels**, since the decompressed scratch file is byte-identical to today's raw format. LRU-cap resident decompressed years (2-3), evict by deleting the regenerable scratch copy. Mutation to a cold year (rare deletes/backfill): decompress to scratch if not already, apply via existing mutate code unchanged, mark dirty, recompress on the next compaction pass.

  **Phase 3 — columnar dtype-specific encoding (optional, highest ratio, highest effort).** Only worth pursuing if Phase 2's generic zstd+dictionary ratio proves insufficient. For maximum ratio on numeric time-series columns specifically: delta/delta-of-delta encoding for timestamps, Gorilla-style XOR encoding for doubles/floats (as used by Facebook Beringei, Prometheus, InfluxDB), frame-of-reference + bit-packing for integers (ClickHouse/Parquet-style), dictionary/RLE for repeated categorical strings, generic zstd fallback for bytes. Requires transposing a row-group (N consecutive rows within a year file) into per-column arrays at compaction time, encoding each column with its dtype-appropriate scheme, then zstd-compressing the result — a real structural addition (a columnar side-format for cold data only; the live/hot format stays row-oriented protobuf for the addressing/skip-parse reasons above).

- [ ] **Distributed XStore: sharding + replication.** Full architecture designed 2026-09-07 — see **[`docs/XStore_Distributed_Architecture.md`](docs/XStore_Distributed_Architecture.md)** for the complete design: component diagram, placement math, proto wire deltas, client-freshness protocol, flow traces (1 client / N clients / failover timeline), failure-mode table, competitive analysis against 15 SOTA systems (kdb+, ScyllaDB, Aerospike, Redis Cluster, Cassandra, TiKV, Kafka, ClickHouse, Druid, InfluxDB 3, VictoriaMetrics, M3DB, TDengine, QuestDB, FoundationDB) with operation-cost estimates, and the full design-review verdict on the abandoned `origin/distributed` branch (kept as reference only — not mergeable, predates current WAL/CRC32C/viewer architecture).

  **Summary — decisions:** 16384 fixed hash slots (`slot = Crc32c(routing_key) & 16383`, Redis Cluster-style), whole-DB-per-node by default with opt-in month-stripe sub-partitioning for hot DBs, `YYYY-MM.XSTORE` month files replacing `<YEAR>.XSTORE`, etcd for cluster membership/slot-map/election (off the request path — consulted on boot and epoch-change only), and a cluster-aware client library holding the slot table directly (1 network hop, matching Aerospike/Scylla shard-aware drivers) with three independent freshness mechanisms: etcd watch (push), per-request epoch + `MOVED`/`ASK`/`TRYAGAIN` redirect (pull correctness backstop), and DEALER heartbeat liveness (fast fault detection, writes to a suspect node error out rather than silently landing elsewhere). Two findings from the design pass reshaped scope: the WAL writes every batch at offset 0 (`XStore_Wal.cpp:742`) so it retains no history to replicate from — WAL segmentation + LSN are hard prerequisites, not follow-ups; and `std::hash<std::string>` (libstdc++ MurmurHash2) is unstable across platforms, so `Crc32c()` is the placement function instead.

  **Phases:** 0 (prerequisites — month files, LSN, WAL segmentation, Batch/Range WAL framing, client `REQ`→`DEALER`, graceful shutdown, `--data-dir` flag, cross-process write coordination — several already independent entries elsewhere in this file) → A (shard-aware routing, no replication yet) → B (WAL-as-replication-stream, async primary→replica, optional semi-sync) → C (etcd-lease failure detection, automatic failover, slot migration/rebalance). Each phase has a benchmark gate in the doc. Do last — biggest architectural change on this list.

  **Notable individual conclusion:** the client library's lockstep `REQ` socket (one in-flight request) is likely XStore's single largest real-world throughput gap versus every competitor profiled — capping one client at ~2,200 ops/s regardless of server speed — and is scheduled to be fixed and benchmarked standalone (Phase 0.5) before any cluster code, so that win isn't misattributed to clustering.
