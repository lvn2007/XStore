# XStore: A High-Performance Time-Series Storage System — Technical Reference

**Purpose of this document:** a complete technical description of the XStore codebase (architecture, data model, storage engine, concurrency design, networking layer, optimization history, testing/benchmark methodology, and known constraints), written for use as background material when writing a scientific/technical paper about the system.

## 1. Provenance and Context

XStore is a research time-series storage system developed at the **Illinois Institute of Technology, Data-Intensive Distributed Systems Laboratory**.

- **Advisor:** Ioan Raicu (iraicu@iit.edu)

The codebase is under active, iterative performance engineering: the git history (see §9) shows a sequence of profile-driven changes, each with a specific measured or reasoned motivation, several of which were tried, reverted, and re-applied after correction. This history is itself a useful narrative of the design trade-offs made.

## 2. System Overview

XStore is a **single-writer-per-file, multi-threaded, RPC-accessed, file-backed time-series row store**. Each logical database ("DB") is a named collection of fixed-width binary rows, physically partitioned into **one file per calendar year** ("year-file"), addressed by direct offset arithmetic from a UNIX timestamp — there is no index, B-tree, or LSM-tree. The row's timestamp *is* its address. `UnaryInsert` durability is backed by a real write-ahead log (§4.12); `BatchInsert`/`RangeInsert` durability is backed by a simpler async data-file fsync coalescer (§4.13) — see those sections for the distinction and what each does and doesn't guarantee.

High-level components:

```
                         ┌─────────────────────────────┐
   Client (C++/Python)   │        ZMQ_Server           │
   XStore_Client  ─req──►│  ROUTER (clients)           │
                         │     ⇅ inproc queue          │
                         │  DEALER → N worker threads  │
                         │     each: REP socket        │
                         │           + XStore instance │
                         └──────────┬──────────────────┘
                                    │ pread/pwrite/mmap/fallocate/pwritev
                                    ▼
                    DataStore/<DBNAME>/<DBNAME>.CFG
                    DataStore/<DBNAME>/<YEAR>.XSTORE  (fixed-width row slots)
                    DataStore/WAL/shard_<N>.WAL        (WAL ring: Unary/Batch/Range insert durability log, §4.19)
```

- **Wire protocol:** Google Protocol Buffers v3, over **ZeroMQ** (ROUTER/DEALER broker pattern, `tcp://` transport).
- **Concurrency model:** one OS thread per configured worker; each thread owns its **own `XStore` instance** (stateless request logic) while several caches (mmap cache, fd cache, config cache) are **static/shared across all instances**, sharded to reduce cross-thread lock contention.
- **Storage:** POSIX files, one directory per DB, one file per (DB, calendar year). Row slots are fixed-width and pre-sized (`ftruncate`) to the whole year's capacity at first touch.
- **Row format:** each row is a serialized `RowData` protobuf message (a `repeated FData` — effectively a variable-typed column list) padded/truncated to the DB's configured `rowLength`.
- **No index/log for addressing:** point/range addressing is arithmetic (`offset = (timestamp − yearFirstEpoch) × rowLength`) — durability, not addressing, is what the WAL ring and its checkpointer provide (§4.12, §4.19; §4.13 is the superseded fsync-coalescer design).

## 3. Data Model

### 3.1 Column value type — `FData`

```protobuf
message FData {
  oneof oneOfData {
    double doubleData = 1;      float floatData = 2;
    int32 int32Data = 3;        int64 int64Data = 4;
    uint32 uint32Data = 5;      uint64 uint64Data = 6;
    sint32 sint32Data = 7;      sint64 sint64Data = 8;
    fixed32 fixed32Data = 9;    fixed64 fixed64Data = 10;
    sfixed32 sfixed32Data = 11; sfixed64 sfixed64Data = 12;
    bool boolData = 13;         string stringData = 14;
    bytes bytesData = 15;
  }
}
```

Each column is a **protobuf `oneof`**, so a column's wire type is self-describing per-row (no fixed schema for column *types*, only for row *count/order*, and rows within a DB are not required to populate every column). This gives per-cell dynamic typing at the cost of oneof tag overhead per column and a runtime type-dispatch switch (`XStore::GetFDataValue`) whenever a column's value must be coerced to a scalar (used by all four aggregate kernels, which normalize every numeric variant to `long double`/`double` for comparison/summation).

### 3.2 Row — `RowData`

```protobuf
message RowData { repeated FData fieldData = 1; }
```

A row is just an ordered list of `FData`. Column identity is **positional** (the Nth `fieldData` entry is column N) — there is no named-column schema stored per row. `RowData` is serialized with `ByteSizeLong()`/`SerializeToArray()` into a **fixed-size slot** (`rowLength`, set once at `CreateDB` time and stored in the DB's `.CFG` file); any row whose serialized size exceeds `rowLength` is **rejected outright** (not silently truncated — this was a historical bug, see §9) and the unused tail of the slot is zero-padded.

A **fully-zeroed row slot is XStore's hole representation** — a byte-0 check (`RowPtr[0] == 0`) on the first serialized byte is used everywhere (scan kernels, `BatchQuery`) as an O(1) "is this row present" test, since a real serialized protobuf message's first byte is always a non-zero varint tag.

### 3.3 Config — `ConfigStruct`

```protobuf
message ConfigStruct {
  string dbName = 1;
  TimeUnit timeResolution = 2;   // SECOND | MILLISECOND | MICROSECOND (client-creatable)
  sfixed32 rowLength = 3;
}
```

Persisted once per DB as `<DataStoreDir>/<DBNAME>/<DBNAME>.CFG` (a single serialized `ConfigStruct`, no framing needed since the file contains exactly one message). `CreateDB` only *accepts* `SECOND`/`MILLISECOND`/`MICROSECOND` (checked against `XStore::PermittedTimeResolution`), but `TimeStruct`/the resolution enum also defines `NANOSECOND`, `MINUTE`, `HOUR`, `DAY` — supported by the time-math layer but not exposed as a creatable resolution at the API boundary.

### 3.4 Wire envelope — `Request`

All 17 RPC kinds (`INFO`, `CREATEDB`, `REMOVEDB`, `REMOVEDBFILES`, `UNARYINSERT/QUERY/DELETE`, `BATCHINSERT/QUERY/DELETE`, `RANGEINSERT/QUERY/DELETE`, `MIN`, `MAX`, `SUM`, `AVG`, `PING`) are carried as one `oneof payload` inside a single `Request` message, so the server parses the wire bytes exactly once and dispatches on `payload_case()` — no separate command-tag pre-parse. This replaced an earlier `RequestType RType` enum field on each message (still present on request messages for backward-compat/logging but no longer the dispatch key).

## 4. Storage Engine

### 4.1 Directory / file layout

```
<BaseDir>/DataStore/<DBNAME>/<DBNAME>.CFG        -- one ConfigStruct, written once at CreateDB
<BaseDir>/DataStore/<DBNAME>/<YEAR>.XSTORE        -- one file per calendar year, fixed-width row slots
```

`BaseDir` = the server process's current working directory at startup (assumption: the binary is run from the directory it lives in — see §11, Constraints). All directory-path members are stored **without** a trailing `/` by convention; joining is always done through a single `JoinPath()` helper, never by string concatenation assuming a trailing slash.

### 4.2 Row addressing

For a DB with resolution `R` and row length `L`, and a timestamp `t` (in units of `R`) whose calendar year (in UTC) is `Y`:

```
FirstEpoch(Y) = start-of-year Y expressed in units of R
offset(t)     = (t − FirstEpoch(Y)) × L
```

The year-file is `ftruncate`'d up front to `(LastEpoch(Y) − FirstEpoch(Y) + 1) × L` bytes (i.e. sized for the year's full capacity in slots) the first time it's opened, so every valid timestamp in that year has a pre-existing slot — inserts and deletes never grow/shrink the file (deletes use `fallocate64(FALLOC_FL_PUNCH_HOLE | FALLOC_FL_KEEP_SIZE)`, a sparse-file hole-punch that frees the underlying blocks but keeps the file's logical size and slot addressing intact).

### 4.3 Year-bucketing math — `TimeStruct`

Every insert/query/delete must first determine which year-file a timestamp belongs to and that year's `[FirstEpoch, LastEpoch]` bounds. This is implemented as **closed-form proleptic-Gregorian civil-calendar arithmetic** (Howard Hinnant's `days_from_civil`/`civil_from_days` algorithms), *not* `gmtime_r()`/`mktime()`/`timegm()`:

- `DaysFromCivil(y, m, d)` — days-since-epoch for a given (Y, M, D), pure integer math, no table lookups, no libc TZ database access.
- `CivilFromDays(z)` — inverse: (Y, M, D) for a given day-count.
- `FloorDiv` — floor (not truncating) division, needed so pre-1970 (negative) timestamps bucket to the correct day rather than off-by-one.
- `WeekdayFromDays` — 0=Sunday..6=Saturday directly from the day count (matches `tm_wday`), derived from the fact that day 0 (1970-01-01) was a Thursday.

**Why this matters / design rationale (from in-code commentary and commit `9da4d5f`, "Rewrite TimeStruct on civil-date math"):**
1. **Determinism** — `gmtime_r` results are affected by process TZ/locale state; on-disk row addressing must be identical regardless of host configuration. Closed-form math has no such dependency.
2. **Resolution-awareness** — `ToSeconds`/`FromSeconds` explicitly convert `MILLISECOND`/`MICROSECOND`/`NANOSECOND`/`MINUTE`/`HOUR`/`DAY` timestamps to/from whole seconds before calendar decomposition. A prior implementation path (`gmtime_r` called directly on the raw integer) implicitly assumed "raw value = whole seconds", silently mis-bucketing MILLISECOND/MICROSECOND databases into the wrong year's file — a correctness bug fixed by routing every year-bucketing decision through `TimeStruct`.
3. **Performance** — no syscall / libc calendar-table lookup per row. `BatchInsert`/`BatchQuery`/`RangeInsert` additionally exploit that input is (or is sorted to be) timestamp-ascending: a `TimeStruct` is only reconstructed on an actual year crossing (comparing against the previous row's cached `[FirstEpoch, LastEpoch]` window), not per row.

### 4.4 Config cache — sharded `CfgMap`

```cpp
struct CfgShard { std::unordered_map<std::string, ConfigStruct> Map; std::shared_mutex Mutex; };
static constexpr size_t CfgShardCount = 16;
static std::array<CfgShard, CfgShardCount> CfgShards;
```

`GetOrLoadCfg` is the **first thing every single RPC calls** (every insert, query, delete, and all four aggregates) — the hottest piece of shared state in the system, even though the fast path only takes a *shared* (read) lock. It is sharded by `hash(dbName) % 16` specifically to spread that per-call shared-lock acquire/release across 16 independent cache lines instead of one process-wide cache line hit by every worker thread on every call. Fast path: shared-lock lookup; miss path: exclusive lock + double-checked re-lookup + `fopen`/`ParseFromFileDescriptor` from the `.CFG` file, then insert. No eviction (the config set is small and static per DB — bounded by DB count, not row count).

### 4.5 Mmap cache — sharded MRU, used by read paths that scan sequentially

```cpp
struct MappedFile { void *Base; size_t Len; };
struct MmapShard {
    std::list<std::pair<std::string, MappedFile>> Lru;
    std::unordered_map<std::string, ...::iterator> Index;
    std::mutex Mutex;
};
static constexpr size_t MmapShardCount = 64, MmapCacheCap = 256;   // 4 slots/shard
```

Used by `RangeQuery` and all four aggregate scans (`WalkYearSpan` → `GetOrMapFile`). Keyed by full file path, sharded by `hash(path) % 64`. Fast path (already-mapped): lock only the owning shard, look up, MRU-promote (`list::splice`), return the base pointer. Miss path: `open()`/`fstat()`/`ftruncate()`/`mmap(PROT_READ, MAP_SHARED)` are all done **without** holding the shard lock (these are syscalls whose cost scales with file size/disk state — holding the mutex across them would serialize every other thread hashing to the same shard, for any DB, for the syscall's duration); the lock is re-acquired only to install the result, with a double-checked race: if another thread mapped the same file first, the redundant mapping is `munmap`'d and the winner's is used. Bounded to 256 total resident mappings (4 per shard) via LRU eviction on insert.

**Why sharded (not one global mutex + MRU list):** a cold-started server hit by many concurrent first-touches (N threads each first-mapping a different year file at once) previously serialized entirely on one mutex for the lookup+promote step even though the actual open/mmap work was already unlocked. Two threads touching *different* files now usually land in different shards and share no lock at all; only same-file (or same-shard-hash-collision) races still serialize.

**Eviction race fix (commit `d6b9ffe`):** each shard entry is a `shared_ptr<MappedFile>`, not a bare `MappedFile`, and `GetOrMapFile` returns a `shared_ptr<void>` aliased onto that control block rather than a raw `void*`. Previously, LRU eviction (or an explicit `EraseMappedFile`/`EraseMappedFilesUnderPrefix`) called `munmap()` unconditionally as soon as an entry aged out, with no coordination against a thread still mid-access on a raw pointer it had read out of the cache earlier — a use-after-unmap race, reproduced under concurrent RND inserts once the working set exceeded `MmapCacheCap`. The `shared_ptr`'s refcount now tracks every outstanding `GetOrMapFile()` caller in addition to the cache's own slot: eviction/erase only drops the *cache's* reference, and the custom deleter's `munmap()` doesn't run until the last holder — cache or in-flight caller — releases theirs. Callers must keep the returned `shared_ptr` alive for as long as they touch the mapping; that's what defers the `munmap()` past a concurrent eviction.

### 4.6 File-descriptor cache — sharded MRU, used by write paths and point reads

```cpp
struct FdShard { std::list<std::pair<std::string,int>> Lru; ...Index; std::mutex Mutex; };
static constexpr size_t FdShardCount = 4, FdCacheCap = 8;   // 2 slots/shard
```

Used by `UnaryInsert`/`UnaryQuery`/`BatchInsert`/`BatchQuery`/`RangeInsert` via `pwrite()`/`pread()`. Structurally identical MRU-shard design to the mmap cache, but deliberately **much smaller** (8 total vs. 256): an fd-open miss is cheap (microseconds, no page-fault-time block allocation to hide behind an unlocked window), so the cache only needs to cover the handful of year-files actively being written/read at once, not amortize an expensive miss. Fewer shards (4, not 64) for the same reason — with a cap this small, 64 shards would leave under one slot each.

`IsFdCached()` (peek-only, no open/creation) is used by `UnaryQuery` (and, since commit `8c6c4fc`, `BatchQuery`) to test file existence without a `stat()` syscall on a warm cache: only files opened via `GetOrOpenFile` are ever cached, and both removal paths (`EraseOpenFile`/`EraseOpenFilesUnderPrefix`) drop the cache entry in the same call that deletes the file, so a cache hit is itself proof the file exists.

**Eviction race fix (commit `d6b9ffe`), same defect class as the mmap cache above:** entries are `shared_ptr<int>`, and `GetOrOpenFile` returns a `shared_ptr<int>` rather than a bare `int`. Eviction/`EraseOpenFile`/`EraseOpenFilesUnderPrefix` previously `close()`'d the fd unconditionally, racing a thread still mid-`pwrite()`/`pread()` on that exact fd via an earlier `GetOrOpenFile()` return value — either a clean `EBADF` or, worse, a silent write into the wrong file if the closed fd number got reused by an unrelated concurrent `open()` before the racing `pwrite`/`pread` ran. `FdCacheCap`'s small size (8, process-wide) made this easy to hit once more than a handful of year files were concurrently hot. As with the mmap cache, the deleter's `close()` is deferred until every holder — cache and in-flight callers — has released its copy; `BatchDelete` and `RangeDelete` (previously `fopen`/`fclose`-per-call for their `fallocate64()` punches) were also switched onto this cached-fd path in commit `8c6c4fc`, both holding the `shared_ptr` through the `fallocate64()` call for the same reason.

### 4.7 Insert path: `pwrite()` vs. mmap write-fault

**Design decision, reverted once and re-applied (commits `2713d92` → `c33a4cf` (revert) → `9e12711` (reapply)):** `UnaryInsert`/`BatchInsert`/`RangeInsert` write via `pwrite()` into a cached fd, *not* a `memcpy` into a cached `PROT_WRITE` mmap region. Rationale: a `pwrite()` into a still-sparse region is a buffered write whose actual block allocation is deferred to async writeback — same cost whether the target offset is sequential or random. An mmap write-fault into an untouched page **cannot** defer that: it must synchronously allocate a real block before the fault returns, making random-offset (RAND) inserts far more expensive than sequential (SEQ) ones under the mmap-write design. `pwrite()` removes that asymmetry.

**Read path is asymmetric on purpose:** `RangeQuery` and the aggregate scans (`WalkYearSpan`) *do* use the mmap cache (`GetOrMapFile`) because they walk a file in sequential offset order, where mmap's page-fault-on-touch model plus kernel readahead is a net win, and each mapping is reused across many rows in one call. `UnaryQuery` and `BatchQuery`, by contrast, use `pread()` on a cached fd:
- `UnaryQuery`: a single random point read — mmap would pay a synchronous major page fault on nearly every call with no reuse to amortize it.
- `BatchQuery`: row order is *request* order (client-controlled, potentially scattered across the year's full offset span), so mmap's readahead prefetches pages the loop will never touch, and a per-call `madvise(MADV_RANDOM)` to suppress that isn't free once part of the mapping is already resident. A plain `pread()` per row sidesteps all of this.

### 4.8 Delete path

`UnaryDelete`/`BatchDelete`/`RangeDelete` all use `fallocate64(fd, FALLOC_FL_PUNCH_HOLE | FALLOC_FL_KEEP_SIZE, offset, length)` under a write lock spanning the punched range — this deallocates the underlying disk blocks (returning them to the filesystem) while keeping the file's logical size and slot addressing unchanged, so the hole reads back as all-zero bytes (XStore's hole sentinel, §3.2) without any special-case "row deleted" flag.

`BatchDelete` cannot coalesce its `fallocate64` calls the way `WriteRowGroupToFile` coalesces writes (§4.9): the requested timestamps are scattered, not necessarily contiguous, and punching one big range spanning the group's min-to-max offset would also deallocate *other* rows sitting in the gaps between the requested points. The **lock**, however, is still taken once over the whole min-to-max span (harmless to over-cover a lock, unlike a hole-punch).

### 4.9 Write coalescing — `WriteRowGroupToFile`

Shared by `BatchInsert` and `RangeInsert` (`include/XStore/XStore_Internal.h`), templated on an `EntryAccessor` lambda so it works over either message type without materializing an intermediate row vector. Both feed it a `YearBucketMap` (`std::vector<std::pair<year, vector<rowIndex>>>` built by `AppendToYearBucket`, a linear scan over existing buckets before appending a new one) — replacing an earlier `std::map<year, vector<rowIndex>>`, since commit `8c6c4fc`: a single request realistically spans only a handful of distinct years, so a flat vector (no per-key tree-node allocation, no pointer-chasing, whole bucket list fits in a couple cache lines) beats a tree map for that small K. `BatchDelete`/`RangeDelete` (which don't route through `WriteRowGroupToFile`, since deletes can't always coalesce, §4.8) were switched to the same `YearBucketMap`/`AppendToYearBucket` in the same commit. `BatchQuery`'s bucket map is explicitly re-sorted by year after building (unlike `Batch`/`RangeInsert`, whose responses are just a status string) to keep its response chronological across years — matching the old `std::map`'s always-sorted iteration order, which mattered specifically when `SortTime=false` lets buckets get created in request order rather than year order.

1. Take one `FileRangeLockGuard` (WRITE) spanning the whole year-group's min-to-max byte offset — **not** one lock per row (see §5.1 for why whole-span won over per-row after being tried at both extremes).
2. Filter to `Valid` rows whose serialized size fits `rowLength` (oversized rows are rejected, not truncated — a correctness fix, see §9).
3. Scan `Valid` (offset-sorted) for **maximal contiguous runs** — adjacent rows whose offsets differ by exactly `rowLength` with no gap.
4. Serialize each run into one thread-local scratch buffer (grown, never freed, reused across calls) and issue **one `pwrite()` per run**, not one per row.

A fully sequential batch collapses to a single run → a single `pwrite()` for the entire group (mirroring the syscall-coalescing a buffered `fwrite()` stream gets for free). A fully scattered (RAND) batch degrades to one run per row — same syscall count as the naive per-row approach, never worse.

### 4.10 Directory scan / `InfoQuery`

`InfoQuery` enumerates every DB directory and every file within it (`std::filesystem::directory_iterator` + `stat()` per file for `st_blocks × 512` allocated-size accounting), fetching each DB's config through the same shared `CfgMap` cache every other operation uses rather than a fresh `fopen`+parse per DB — relevant because this is a status/monitoring endpoint likely to be polled repeatedly.

### 4.11 Path caching — `CachedDbBasePath` / `CachedYearFilePath`

Two `thread_local` hashmap memos (`include/XStore/XStore_Management.cpp`), introduced in commit `62ef571` to replace an earlier **single-entry** memo:

```cpp
const std::string& CachedDbBasePath(const std::string &dbName) const;                  // dbName -> "<DataStoreDir>/<dbName>"
const std::string& CachedYearFilePath(const std::string &dbBasePath, unsigned short year) const;  // (dbBasePath, year) -> ".../<year>.XSTORE"
```

`DbBasePath()`/the `fmt::format`-built year-file path are both pure (no I/O), but every single op function (Unary/Batch/Range Insert/Query/Delete, all four aggregates via `WalkYearSpan`) calls them unconditionally on every call — a heap allocation paid even on an otherwise-fully-cached fast path. The original design was a **single-entry** `thread_local` memo (last dbName/year wins, invalidated on any change) — fine for a worker thread that stays on one DB/year across consecutive requests, but it thrashes (misses on nearly every call) under a RND-pattern workload where a thread bounces between a handful of distinct years in no particular order (see `UnaryInsertRandomThroughput` in `XStorePerfTest.cpp`). The hashmap version stays warm regardless of access order, since a real dataset's year range is small enough to fit entirely. `CachedYearFilePath` is keyed by `dbBasePath` (not `dbName`) since callers that only have `dbBasePath` in hand (e.g. `WalkYearSpan`, shared by all four aggregates) don't need to separately thread `dbName` through just for this.

**Cross-directory aliasing bug (fixed in commit `8c6c4fc`):** `CachedDbBasePath`'s outer key was `dbName` alone. In production this is safe — `DataStoreDir` is fixed for the life of a server process — but the test suite `chdir()`s into a fresh scratch directory per test case while reusing the same `dbName` (e.g. `"TESTDB"`) across nearly every test; a `dbName`-only memo doesn't expire when a test's directory is torn down, so a later test's lookup for `"TESTDB"` could silently return an earlier, already-deleted test's path. Fixed by keying on `(DataStoreDir, dbName)` — an outer map keyed by `DataStoreDir`, inner map keyed by `dbName` — which collapses back to the single-outer-entry case in production (one `DataStoreDir` per process) while giving each distinct directory its own inner map in tests.

### 4.12 `UnaryInsert` durability — the write-ahead log

`UnaryInsert`, `BatchInsert` and `RangeInsert` (SYNC and ASYNC) are routed through the WAL; `BatchInsert`/`RangeInsert` since 2026-09, one record per (db, year) group (see the note in §4.13). Since 2026-10 the log is a checkpointed ring with LSNs (§4.19); the description below is updated to match. Each `WalDurabilityMode` maps to a distinct processing model:

- **How it processes the request:** the row is framed into a WAL record (`[u32 recordLen][u32 crc32c][u64 lsn][u16 dbNameLen][u16 rowLength][i32 timeResolution][u32 rowCount][dbName][epochTime + row bytes]...`; the CRC covers the LSN, §4.19) and handed to `EnqueueWalRecord`, which hashes the DB's base path onto one of `WAL_SHARD_COUNT` (8) shards so one DB's writes funnel through one shard's group-commit window (`WAL_SHARDS_PER_DB`=4 additionally salts by calling-thread id, which on the glibc here does not actually spread threads: one DB ≈ one shard, §4.19 limits). A dedicated writer thread per active shard (`WalWriterLoop`) waits up to `WAL_GROUP_COMMIT_WINDOW_US` (10ms) for the first record, then lingers over an **adaptive** gather window (`WAL_GATHER_WINDOW_MIN_US`=50 to `WAL_GATHER_WINDOW_MAX_US`=250, driven by a per-shard EMA of recent batch sizes) up to `WAL_BATCH_MAX_RECORDS`=256 — a Kafka-style `linger.ms`+`batch.size` dual trigger. The batch is appended with `pwritev()` (vectored I/O, zero-copy of row bytes) into the shard's **ring file** (§4.19: fixed size, pre-zeroed at creation, so the commit's one `fdatasync()` never extends the file and there is no oversized-write `fsync()` fallback), then, once the ring bytes are durable, applied row-by-row to the real `.XSTORE` data file, and each record's completion semaphore is resolved with the true durability result. Large Batch/Range records skip the ring entirely (direct path, §4.19).
  - **SYNC:** the caller blocks until both the WAL `fdatasync()` and the data-file apply succeed. Guarantee: return only after the write is durable on stable storage — including across an OS crash or power loss since 2026-10 (the ring record is retained until the data file is synced, §4.19; residual risks listed there). Cost: one `fdatasync()` per group-commit window, amortized across every record that landed in that window.
  - **ASYNC** (default): the caller's enqueue returns immediately after a lock-free hand-off; the writer thread's group-commit loop above still runs, just off the request's critical path. Guarantee: eventual durability within one gather-window's worth of latency, not immediate. A crash inside that window loses the record — the same trade every ASYNC durability mode makes.
  - **BYPASS:** `ApplyWalRecord` runs inline on the calling ZMQ worker thread, skipping the WAL entirely — no queue, no CRC, no second write. Durability bound is OS writeback timing (`dirty_expire_centisecs`, ~30s default), nothing more.
- **Crash recovery:** `ReplayWal()` runs at `InitDB()`, before any DB is trusted. For each `shard_<N>.WAL` ring it starts at the header's `checkpoint_lsn`, CRC- and LSN-validates each record (so a torn write or a leftover of the previous lap ends the scan), replays valid records via `ApplyWalRecord`, `fdatasync`s the data files they touched, and only then persists a new `checkpoint_lsn`; a crash during replay replays again (idempotent). Nothing is overwritten at offset 0 and nothing is invalidated: the checkpoint only moves forward, after the data it covers is synced. A pre-ring WAL file is replayed once and converted. A clean shutdown runs a final checkpoint cycle (`Checkpointer::StopAfterFinalCycle`, §4.18/§4.19), so a graceful restart replays nothing. Details, fencing rules and limits: §4.19.
- **Pros:** SYNC gives a real, provable durability guarantee at group-commit-amortized cost, not per-record cost. ASYNC gives near-zero-latency inserts with a bounded, known loss window. Crash recovery is `O(records since the last checkpoint)`, not `O(database size)`, and replay itself needs no index reconstruction (the indexes of replayed years are rebuilt separately, §4.18).
- **Cons:** the log is one fixed-size ring per shard (no segments, no archive), and the WAL writer still applies to the data file synchronously in the same loop rather than via a decoupled background materializer — see `TODO.md`. LSNs and checkpointing exist since 2026-10 (§4.19); the ring's limits (stall when the checkpointer cannot keep up, accepted residual risks) are listed there.
- **What's novel:** the WAL is **record-oriented, not page-oriented**, exploiting XStore's own O(1) timestamp→offset addressing — recovery never needs to reconstruct or traverse an index, unlike a conventional database's WAL, which typically must also log page/tuple/index metadata. This was the founding design thesis for XStore's WAL (see git history around commits `be5d8d41`..`c748f3ee`) and is largely realized: recovery is genuinely just "verify CRC, compute offset, rewrite."

### 4.13 `BatchInsert`/`RangeInsert` durability — the async data-fsync coalescer

> **Superseded (2026-09 / 2026-10).** This section is the original design and is kept as history. `BatchInsert`/`RangeInsert` SYNC and ASYNC no longer use the data-fsync coalescer: since the ASYNC Batch/Range WAL work (`docs/superpowers/plans/2026-09-08-async-batch-range-wal.md`) each (db, year) group is one `WalRecord` handed to `EnqueueWalRecord` like a unary insert (only BYPASS applies inline), and `ScheduleAsyncDataFsync`/`DATA_FSYNC_COALESCE_WINDOW_US` no longer exist in the source. Since 2026-10 records of 1 MiB or more skip the ring and are applied then `fdatasync`ed directly, and the rest are replayed from the ring after a crash; see §4.19. The text below no longer describes the code.

Batch and Range inserts do **not** go through the WAL above. Rows are already written sequentially via the coalesced `pwrite()`s described in §4.9, so instead of a separate log, durability is handled per touched file descriptor:

- **How it processes the request:** after `WriteRowGroupToFile` returns, the same `WalDurabilityMode` enum (reused, with a narrower meaning here) picks the action per touched year-file: **SYNC** calls `fdatasync(fd)` inline, before the reply is built — verified to genuinely block the reply on completion, with a failed fsync surfaced as an error rather than masked as success. **ASYNC** calls `ScheduleAsyncDataFsync(fd)`, which only inserts the fd into a pending map and returns immediately; a single background coalescer thread wakes every `DATA_FSYNC_COALESCE_WINDOW_US` (1000µs), swaps out the pending map, and issues one `fdatasync()` per distinct fd. **BYPASS** does nothing beyond the `pwrite()`s already done, relying on OS writeback timing alone.
- **Pros:** SYNC's guarantee is genuinely equivalent to the WAL's SYNC guarantee for this write pattern — no correctness gap. ASYNC deduplicates fsyncs across many touched files into one coalescer tick, cheaply.
- **Cons (the real, narrower gap — verified, not assumed):** ASYNC here has the same bounded (~1ms nominal) crash-loss window UnaryInsert's own ASYNC WAL path has, but **lacks the WAL's CRC-framed record and replay-on-restart** — if a crash lands inside that window, or the data-file write itself was torn, there is no independently-durable log to recover from. This is a real, if narrow, asymmetry with UnaryInsert's WAL and is tracked in `TODO.md` ("give ASYNC Batch/Range Insert a real log-then-apply safety net").
- **What's novel:** deferring and deduplicating fsyncs by fd, rather than by record, is a much simpler mechanism than a full WAL and is sufficient for SYNC's guarantee — the design deliberately doesn't build a second WAL implementation for a write pattern (large, already-sequential/coalesced writes) where a full log-then-apply model buys comparatively little over `fdatasync` at the OS-file granularity.

### 4.14 Zone-map secondary index — non-timestamp-column acceleration

XStore's only index is the timestamp→offset formula (§4.2); a predicate or aggregate on any other column otherwise forces a full scan of every row's slot across the queried range. The zone map is a per-`(db, year)` sidecar file, `<YEAR>.zmap`, holding one fixed-size `{min, max, sum, sumSq, firstValue, lastValue, validCount, nullCount, firstRowIndex, lastRowIndex}` summary per (block, tracked-column) pair — a block is a contiguous run of rows sized to a target byte budget, not a fixed row count. `MinAggregate`/`MaxAggregate` use it to skip whole blocks that can't hold a better answer; `SumAggregate`/`AvgAggregate` use it to add a fully-covered block's precomputed sum/count with zero row scan; `VarianceAggregate`/`StddevAggregate` (added by the variance/stddev follow-on plan) additionally use the `sum_sq_value` field below for the same fully-covered-block pushdown, via the textbook `Var = (Σx² − (Σx)²/n) / (n−1)` identity; `OhlcAggregate` (added by the OHLC follow-on, 2026-09-19) uses `first_value`/`last_value` for Open/Close and `min_value`/`max_value` (the same fields MIN/MAX already use) for High/Low, all four returned from one block walk. Full design and rejected alternatives: `docs/superpowers/plans/2026-09-14-zone-map-secondary-index.md` (base feature), `docs/superpowers/specs/2026-09-15-variance-stddev-aggregate-design.md` (`sum_sq_value`/v2 format/rebuild follow-on), and `docs/superpowers/specs/2026-09-19-ohlc-bar-aggregate-design.md` (`first_value`/`last_value`/v3 format follow-on).

- **Block-size derivation:** `RowsPerBlock(rowLength) = ZONE_MAP_TARGET_BLOCK_BYTES / rowLength` (2MiB target, floor division, minimum 1). Byte-size-derived rather than a fixed row count (e.g. ClickHouse's `index_granularity=8192`) because XStore's fixed-width `rowLength` varies enormously across DBs — a fixed row count would make the zone map's own per-block I/O cost swing wildly with row width, where a byte-size target keeps it roughly constant.
- **Tracked-column cap, and why:** XStore has no declared column schema (`CreateDB` takes only `rowLength`, a byte budget, never a column count), so there's no natural "number of columns" to size the zone map against. Deriving one from `rowLength` (e.g. `rowLength / 2`) was tried and rejected — checked against a 1536-byte wide-row DB, it inflates to ~708MB/year (see `TODO.md`'s "Verified — no action needed" history for that check). Instead, every zone map tracks a cap, `ZONE_MAP_MAX_TRACKED_COLUMNS` = 64 columns, used as the *global default* — see the per-DB high-water-mark refinement below for how the effective cap actually used for a given DB can differ from this default. A column index at or past the effective cap gets no acceleration and always falls back to a full scan for that column — always correct, just not accelerated.
- **`sum_sq_value` and the v1→v2 format bump:** `ZoneMapEntry` (`include/XStore/XStore_ZoneMap.h`) grew `double sum_sq_value` — folded on every `UpdateRow` call the same write-through way `sum_value` always was (see the crash-safety argument below) — never a separate/delayed pass. `ZoneMapFileHeader.version` (`ZONE_MAP_VERSION`) was bumped `1 → 2` for this change, and `ZoneMapFile::Open()` **discards and reinitializes** (truncates the file, calls `WriteFreshHeader`) any file whose on-disk `version` doesn't match the current `ZONE_MAP_VERSION`, rather than migrating it in place — there is no in-place migration path at all, for this or any later bump. This is deliberate, not a shortcut: an older file's raw bytes are a genuinely different, incompatible struct layout, so reinterpreting them under a newer layout would misread arbitrary bytes as the new fields, not just miss them; and because the zone map is by design fully re-derivable from the real `.XSTORE` row data (it's a cache/index, never the source of truth), discarding a stale-version file costs one rebuild pass and zero real data loss — see the startup rebuild below for exactly when that pass runs. `ZoneMapFileVersionTest.OpenDiscardsStaleVersionFileInsteadOfMisreadingIt` (`tests/integration/XStoreZoneMapTest.cpp`) hand-writes a v1-shaped header to prove this discard path, not a crash or garbage read.
- **`first_value`/`last_value` and the v2→v3 format bump (OHLC, 2026-09-19):** `ZoneMapEntry` grew four more fields for the OHLC follow-on — `double first_value`/`last_value` (the chronologically first/last numeric value folded into this block, i.e. Open/Close — distinct from `min_value`/`max_value`, which are value-extremes, i.e. High/Low) and `uint64_t first_row_index`/`last_row_index` (the `row_index` each was folded from, needed so an out-of-order/backfill insert can correctly tell whether it's chronologically more extreme than what's already recorded, the same way `min_value`/`max_value` compare against the running value rather than trusting insertion order — `ZoneMapFileTest.ConcurrentUpdateRowWithDistinctRowIndicesConvergesToCorrectFirstAndLast` and `XStoreTest.OhlcAggregateOutOfOrderBackfillInsertStillPicksChronologicalOpenAndClose` both exist specifically to catch a regression to first-observed-wins). `ZoneMapEntry` is now **80 bytes** (48 → 80), `static_assert`-pinned. `ZONE_MAP_VERSION` bumped `2 → 3`; `ZoneMapFileVersionTest.OpenDiscardsV2FileInsteadOfMisreadingIntoV3Layout` proves the same discard-not-migrate path for this bump.
- **Per-DB `columnCount` high-water mark:** `ConfigStruct` now carries a per-DB `columncount` field that auto-grows (monotonically, never shrinks) instead of every DB unconditionally using the flat global `ZONE_MAP_MAX_TRACKED_COLUMNS` default. `XStore::EffectiveTrackedColumnCount(cfg_struct)` returns `cfg_struct.columncount()` when it's `> 0`, else falls back to the global default (so a DB that's never observed a wide row yet, or predates this field, behaves exactly as before). `XStore::MaybeGrowColumnCount` is called on every insert path (`XStore_UnaryOps.cpp`/`XStore_BatchOps.cpp`/`XStore_RangeOps.cpp`) after the zone-map update, and only ever raises the recorded count: a cheap shared-lock read compares the observed row's column count against the cached value first (the steady-state fast path, no I/O), and only a genuinely wider row takes an exclusive lock, compare-and-sets the in-memory `CfgShard` entry, and durably rewrites that DB's `.CFG` file — compare-and-persist inside the same critical section so two threads racing with different observed widths can never regress the persisted value or land their disk writes out of order relative to each other.
- **`InitDB()`-integrated startup rebuild:** `XStore::InitDB()` (called once per `data_store_dir`, guarded by a `static` initialized-dirs set — see §5.2 — so this runs once per process before any worker thread can serve a request against that directory) now calls `XStore::RebuildStaleZoneMapsForDb(db_name, db_base_path, cfg_struct)` for every DB it loads, right after that DB's `ConfigStruct` is parsed and cached, and after WAL replay. For each `<year>.XSTORE` file under that DB, `XStore::ZoneMapNeedsRebuild(zmap_path, desired_tracked_columns)` flags it stale if its `.zmap` sidecar (a) doesn't exist, (b) can't even be read back as a full header, (c) has the wrong magic, (d) has `version != ZONE_MAP_VERSION` (the v1→v2 case above), or (e) has a `tracked_column_count` that doesn't match that DB's *current* `EffectiveTrackedColumnCount` (the high-water mark above, so a DB whose column count has since grown gets its older, narrower zone maps rebuilt too — including widening them, never shrinking, per `ZoneMapFile::Open`'s own asymmetric width-mismatch guard). Every flagged year is rebuilt by `XStore::RebuildOneYearZoneMap`: it evicts any already-warm process-wide registry entry for that `(db, year)` key (so a stale in-memory instance from WAL replay can't mask the rebuild), unconditionally truncates the `.zmap` to force a genuinely empty v2 header at the authoritative width, then does a raw `pread`-per-row scan of the whole data file, parsing each row (`XStore_Proto::RowData`) and folding it into the zone map via `BuildZoneMapObservations`/`UpdateRow`. All years a DB needs rebuilt are fanned out across `XStorePreadPool::ParallelFor` (§6.2's shared, bounded, process-wide pread pool — not one unconditional thread per year) rather than rebuilt serially. Crucially, this entire pass runs **synchronously inside `InitDB()`, before it returns** — never deferred to a background thread and never run lazily on the request path — so no worker thread can ever serve a query or aggregate against a zone map `InitDB()` already knows is stale. `InitDbRebuildsZoneMapForPreExistingDataWithNoSidecar` (`tests/integration/XStoreZoneMapTest.cpp`) covers the missing-sidecar case end-to-end (raw-written historical data, no `.zmap` at all, `InitDB()` rebuilds it, then a `VarianceAggregate` call is checked against an independently-computed answer).
- **Crash-safety argument — write-through, no dirty state (process crash; for OS crash / power loss see the dirty-flag protocol in §4.18):** every `ZoneMapFile::UpdateRow` call `pwrite()`s its block's entries back to disk before returning, always — there is no buffered "dirty" state a crash can lose. The zone map's own update is applied inside `ApplyWalRecord` (`XStore_Wal.cpp`), at the exact same moment as the row's real data-file write and under the same success/failure check, not eagerly when `UnaryInsert`/`BatchInsert`/`RangeInsert` is first called — for ASYNC durability mode (the default for Batch/Range), the real write happens later on a WAL writer thread, and updating the zone map any earlier would let it claim a row before a crash proves it was never durably written, corrupting a later `Sum`/`Min`/`Max` result. A rejected earlier design cached a block's entries in memory and flushed only on LRU eviction, treating a still-cached block as untrustworthy for pruning — but a block already flushed once, then updated further before a crash before its next eviction, leaves a **stale-but-present** on-disk baseline that a later reload accumulates on top of and eventually re-flushes looking complete: silently and permanently under-representing that block with no way to detect it later. Write-through closes that window structurally rather than by convention. The invariant this buys: a **false positive** (failing to prune a prunable block) is always acceptable; a **false negative** (skipping a block that contains a real match, or a pushed-down sum including rows that were never truly written) is never acceptable, and this design has no path to one.
- **Measured file size (computed, not estimated — `ZoneMapEntry` is 80 bytes, `static_assert`-pinned; `ZoneMapFileHeader` is 24 bytes; both verified by compiling against the real headers), one full 365-day SECOND-resolution year at the 64-column cap:**

  | Row shape | rowLength | RowsPerBlock | Blocks/year | Zone-map file | Data file (`.XSTORE`) | Ratio |
  |---|---:|---:|---:|---:|---:|---:|
  | Narrow | 64 B | 32,768 | 963 | 4,930,584 B (4.701 MiB) | 2,018,304,000 B (1.880 GiB) | 0.2443% |
  | Wide | 1536 B | 1,365 | 23,104 | 118,292,504 B (112.793 MiB) | 48,439,296,000 B (45.113 GiB) | 0.2442% |

  Both shapes land at the same ~0.24% of the underlying data file's size — the fixed 64-column cap (not a `rowLength`-derived column count) is what keeps this ratio constant instead of blowing up for wide rows, confirming the original brainstorm's "single-digit MB, near-zero memory" framing holds in practice once corrected to a capped column count. This ratio is up from ~0.15% in the pre-OHLC (48-byte entry, v2) design and ~0.12% in the original (40-byte entry, v1) design — exactly the 80/48 ≈ 1.667× and 80/40 = 2× entry-size growth predicts at each step, since block/row layout is otherwise unchanged. This is an exact recomputation from the same formula (header + blocks × columns × entry_size), not a re-run of the original measurement methodology.
- **Performance benchmark — not yet run from this environment.** Per `docs/Cross_Machine_Access_And_Benchmarking.md`, XStore's real before/after benchmarks run on the Mystic cluster at IIT, driven from a `dubuntu` host reachable only via SSH from a machine with that access — this development session has no network route to `dubuntu` (`ssh dubuntu` → "No route to host"). Two measurements remain open, to be run from a session with that access, before this feature can be called performance-verified rather than just correctness-verified (147/150-plus tests, full suite, as of this feature's last commit):
  - **Insert-path overhead:** `INSERT_UNARY_SEQ`/`INSERT_UNARY_RAND`/`INSERT_BATCH_SEQ`/`INSERT_BATCH_RAND`, full thread sweep, baseline = `main` at this branch's fork point — measures the extra `pwrite()` every insert now pays for its zone-map update.
  - **Query-side pruning win:** `MinAggregate`/`SumAggregate` wall-clock over a wide multi-block range, before vs. after this feature, on a synthetic needle-in-haystack dataset shaped so most blocks are prunable — no existing Mystic workload tag varies column selectivity enough to exercise this on its own.

### 4.15 Categorical/high-cardinality index — `FindByValue` equality-lookup acceleration

XStore's zone map (§4.14) accelerates `MIN`/`MAX`/`SUM`/`AVG`/`VARIANCE`/`STDDEV`/`OHLC` — numeric-range/aggregate queries — but has nothing to offer an **equality** predicate (`columnIdx == value`, e.g. `symbol == "AAPL"` or `status == 3`): a zone map's `{min, max}` range can't rule out a block containing one specific value the way it rules out a block for `MIN`/`MAX` pruning. `FindByValue` is a new RPC (`FINDBYVALUE = 25`, `proto/XStore.proto`) that returns every full row in `[startTime, endTime]` where `columnIdx` equals a given `FData` value, accelerated by a new per-`(db, year)` sidecar file, `<YEAR>.catidx`, deliberately kept **separate from `.zmap`** (independent version churn, no cache-footprint regression to existing zone-map-only queries, isolated corruption blast radius — `docs/superpowers/specs/2026-09-21-categorical-high-cardinality-acceleration-design.md`). Reply reuses `UnaryQuery_REP`'s exact wire shape (`repeated {timestamp, data}`), field-numbered identically to `RangeQuery_REP`.

- **Not built on `WalkYearSpanParallel`, unlike every other aggregate op.** The original plan sketched `FindByValue` on the shared `WalkYearSpanParallel` traversal §6.4 uses for `MIN`/`MAX`/`SUM`/`AVG`/etc. That kernel's per-block callback signature has no way to produce a real per-row `epoch_time` without changing all 11+ existing aggregate call sites' shared signature — a row-emitting op (unlike an aggregate, which only ever emits one final scalar) genuinely needs it. Instead, `FindByValue` (`XStore::FindByValue`, `src/XStore/XStore_Aggregates.cpp`) is its own hand-rolled per-year loop, shaped like `RangeQuery`'s own manual loop (`XStore_RangeOps.cpp`) rather than the aggregate machinery: `iter_epoch` is the literal loop variable, so `epoch_time` is always trivially correct, and the loop walks **blocks** (`BlockIndexForRow`/`RowsPerBlock`, the same block geometry `.zmap`/`.catidx` both already share) rather than individual rows, so a bloom/bitmap check can rule out (or fully answer) an entire block at once. This makes `FindByValue` **sequential per query**, not parallel-fan-out like the aggregate ops — matching `RangeQuery`'s own existing precedent, not a regression unique to this feature.
- **`.catidx` file layout** (`CatIdxFileHeader`/`CatIdxFile`, `include/XStore/XStore_CatIdx.h` + `src/XStore/XStore_CatIdx.cpp`):

  ```text
  [CatIdxFileHeader: magic(u32) | version(u32) | tracked_column_count(u32) | block_count(u32) | bitmap_section_offset(u64) | dirty(u32) | reserved(u32)]  -- 32 bytes
  [Bloom section: for block 0..block_count-1, for column 0..tracked_column_count-1: BloomEntry (160 bytes, fixed)]
  [Bitmap section (only present once bitmap_section_offset != 0, i.e. after compaction): repeated per-column directory blocks, appended back-to-back:
     [columnIdx(u32)][entryCount(u32)]
       per entry, sorted by encoded value bytes: [valueLen(u32)][valueBytes][rowCount(u32)][rowIndices: u64 * rowCount]
  ]
  ```

  `CatIdxFileHeader` is 32 bytes (`CATIDX_VERSION` 2: the original 24 bytes — four `uint32_t` + one `uint64_t`, no padding — plus `dirty` and `reserved` `uint32_t`; the dirty-flag protocol is §4.18). `BloomEntry` is a fixed `CATIDX_BLOOM_BYTES_PER_ENTRY = 160` bytes (1280 bits) per tracked column per block, with `k=7` hash functions. **These numbers are known to be undersized for the real block geometry** and are flagged as such in `XStore_Tunables.h`: they were derived for `n=128` distinct values per block, but `RowsPerBlock(row_length)` is `ZONE_MAP_TARGET_BLOCK_BYTES / row_length` (2 MiB / `row_length`) — 32,768 rows per block at `row_length=64`, and only 128 at `row_length=16384`. At a realistic few hundred to few thousand distinct values per block, 1280 bits at `k=7` saturates and the filter's effective selectivity degrades toward **zero pruning**, well before the high cardinalities this feature is named for. This is a **performance** gap only, never a correctness one: a bloom filter can only over-approximate, so a saturated filter simply stops skipping blocks and every query falls through to the always-correct real-scan path. Retuning the two constants needs real cardinality data and benchmarking (larger entries cost disk on every block × every tracked column) and is tracked as a follow-up in `TODO.md`. A block's existence is governed by `header_.block_count`, **not** raw file size — file size includes whatever the appended bitmap section added past the bloom region, and the bloom section's own offset arithmetic (`BloomSectionFileOffset`) can land inside that directory range for a block index that was never actually written; `block_count` is durably bumped only by `FlushBlock` (a real `UpdateRow` mutation), so it stays independent of the bitmap section's size. `EnsureBlockLoaded` reading a never-touched block index (`block_index >= block_count`) zero-fills purely **in memory** and does *not* write to disk — this is a Task-9 fix: the original implementation durably wrote on any cache miss including from `MightContain` (a pure query), meaning a `FindByValue` query over sparsely-populated data would silently grow the `.catidx` file just by being read. The durable write + `block_count` bump for a genuinely new block now happens only in `FlushBlock`, called only from `UpdateRow`.
- **The bitmap directory is a compaction-time snapshot — a *candidate filter* the query path must verify, never an authority on its own.** This is the feature's single most load-bearing invariant, and getting it wrong is exactly what the final whole-branch review caught as its one Critical finding. `CompactOneYearCatIdx` records `{value → [row_index...]}` as it was *at the moment of compaction*; the rows it names can subsequently be overwritten or deleted, and rows carrying the value can subsequently be backfilled without the directory ever learning about them. Two independent mechanisms therefore have to hold together, and neither alone is sufficient:
  1. **Verify before emitting (query side).** `FindByValue` re-decodes every candidate row `LookupExact` returns (`ExtractColumnByIndexSkipParse` + `EncodeFDataForCatIdx`, byte-identical to what the real-scan path does) and emits only those that *still* match. Without this, an overwritten/deleted row that held the value at compaction time is returned as a false positive. This is still far cheaper than scanning the block — only the rows the directory names get decoded, not every row.
  2. **Invalidate on any post-compaction write (write side).** `FlushBlock` invalidates the whole section (`bitmap_section_offset = 0`, `pwrite`+`fdatasync` the header) on **any** bloom write to a file that has a committed bitmap section — not merely one whose bytes would physically overlap the directory. An overlap-only check (the original implementation) never trips for a write into a block index that already existed at compaction time, since `bitmap_section_offset` sits past every such block — precisely the common backfill/overwrite case — so the directory silently drifted from reality while remaining committed. Without this, a row backfilled after compaction is a false *negative*: verification alone cannot help, because such a row is not in the candidate list at all. Invalidation **self-heals**: the next compaction pass sees `HasBitmapSection() == false` (its own idempotency check) and rebuilds the directory from current row data; in the meantime queries correctly fall back to bloom + real-scan. Same "always fully re-derivable from real row data" precedent zone-map's version-bump-discards use elsewhere. It also subsumes the original byte-overlap concern (a backfill growing the bloom section into the directory's bytes), since any such write now invalidates the directory before writing.

  `UpdateRow`/`FlushBlock` against an already-compacted year is rare by construction (compaction only ever targets closed, cold years), so the extra header rewrite is not a hot-path cost.
- **Bloom hash construction — Crc32c + FNV-1a double-hashing.** Each observed value is encoded to canonical bytes via `EncodeFDataForCatIdx` (a one-byte `oneof`-case tag + the value's raw bytes — distinguishes `int64Data=5` from `doubleData=5.0`, exact-type equality rather than the aggregate paths' numeric-coercion-to-double). Two independent hashes are taken of those bytes: `h1 = Crc32c(...)` (XStore's existing hardware-accelerated CRC32C, `include/XStore/XStore_Crc32c.h` — originally the WAL record-framing checksum, repurposed here purely as a fast, well-distributed hash, functionally fine outside its original scope) and `h2 = Fnv1a64(...)` (a trivial from-scratch 64-bit FNV-1a, no external dependency). The two are combined via standard Kirsch-Mitzenmacher double-hashing, `g_i(x) = h1(x) + i·h2(x)` for `i in [0, CATIDX_BLOOM_HASH_COUNT)` (`k=7`), each `g_i(x) mod (entry_size_bytes * 8)` selecting one bit of the 160-byte entry — avoiding `k` independent hash function implementations for one extra hash's cost.
- **Compaction — trigger and cardinality cap.** A background thread (`XStore::StartCatIdxCompactionThread`, spawned once from `main.cpp` after `InitDB`, one dedicated `XStore compaction_store` instance owned for the thread's lifetime — this codebase's established "one instance per worker thread" convention) polls every `CATIDX_COMPACTION_POLL_INTERVAL_SEC` (3600s) via `CompactColdCatIdxForAllDbs`, which walks every DB directory and calls `CompactOneYearCatIdx` for every `<year>.XSTORE` file strictly older than the current calendar year (`year >= current_year` is skipped — compaction only ever targets closed/cold years, never the currently-writing one). `CompactOneYearCatIdx` is idempotent (`HasBitmapSection()` short-circuits an already-compacted year) and does a full raw-`pread`-per-row scan, building `{column_idx: {encoded_value: [row_index...]}}` accumulators; the moment a column's distinct-value count crosses `CATIDX_MAX_BITMAP_DISTINCT_VALUES` (10,000), that column's accumulator is dropped and the column is marked abandoned — it gets no bitmap directory for that year and stays bloom+real-scan-only forever (the cardinality safety valve that lets "automatic bitmap for every tracked column" coexist with near-unique-value columns without unbounded directory growth). `AppendBitmapSection` commits **all** surviving columns' directories in one call — a deliberate signature change from the plan's original one-call-per-column: committing per-column meant only the first column's write was crash-safe (`bitmap_section_offset` went non-zero after that first commit), so a crash during a later column's write left torn bytes *inside* the already-committed, scannable range. One buffer, one `pwrite`+`fdatasync`, then one header commit (`bitmap_section_offset` set + `pwrite`+`fdatasync` again) closes that window.
- **Dangling-reference mitigation in compaction and query (accepted residual risk).** `CompactOneYearCatIdx` originally held a `CatIdxFile&` across its entire multi-minute row scan, while `GetOrOpenCatIdx`'s registry could concurrently evict and destroy that instance under `CATIDX_REGISTRY_CAP` (256) pressure — pressure this feature's own hourly compaction sweep over every `(db, year)` pair now creates for real, not merely "unrelated activity elsewhere." Fixed by not holding the reference across the scan — the registry reference is dropped after the idempotency check and re-acquired fresh immediately before the final `AppendBitmapSection` call, narrowing the dangling-reference exposure window from "the whole scan" to one call. `FindByValue` had the same defect (one `CatIdxFile*` held across a per-block loop spanning up to ~961 blocks at `SECOND` resolution) and got the same treatment: all registry access happens in one scoped block per year segment, before any row work, and no reference is live across candidate verification or row emission (see the query-path tiering bullet). `ApplyWalRecord` still holds a `CatIdxFile&` across its record's run loop — a shorter window than either of the above, and left as-is rather than risk a rushed change to the WAL apply path. None of this is **fully** airtight — a truly race-proof fix would need `GetOrOpenCatIdx` to return `std::shared_ptr<CatIdxFile>` instead of a reference, rippling into every caller across the whole feature — accepted as a very-low-probability residual risk under heavy `(db, year)` churn exceeding 256 resident instances, not silently closed.
- **Query-path tiering — bloom → bitmap candidates → real-scan.** Everything requiring the `CatIdxFile` is pulled out **once per year segment**, before the per-block loop: `GetOrOpenCatIdx` once, one `MightContain` per block in the segment (cheap, one small `pread` per block), and — if `HasBitmapSection()` — one single `LookupExact(column_idx, encoded_value)` for the whole segment, whose sorted row-index list is kept in memory. The `CatIdxFile` reference is then dropped before any row is touched (see the dangling-reference bullet below), and `LookupExact` no longer re-scans the entire year's directory once per "maybe" block. Then, per block: (1) bloom said `false` → **definite absence**, the whole block is skipped, no row touched. (2) Bitmap candidates exist → only the candidate rows falling inside this block (found by `std::lower_bound` into the pre-sorted list) are decoded, each **re-verified against current row bytes**, and emitted only if they still match — a candidate list, not an authority (see the invariant bullet above). (3) Otherwise (bloom says maybe and no usable directory, or column past `tracked_column_count` — always correct, just unaccelerated) the block falls back to a real per-row decode+compare scan, `RangeQuery`-style. Step 1 is the only tier that skips real data, and it is safe precisely because a bloom filter never yields a false negative; step 3 is always correct as a fallback — exactly the zone map's own "false positive OK, false negative never OK" invariant.
- **2GB streaming-result guard (added mid-implementation, not in the original plan).** `RangeQuery`'s existing client-side chunk-reassembly vulnerability (the client reassembles every streamed chunk into one buffer before `ParseFromArray`/`ParseFromString`, so a >2GB reassembled result corrupts on the client regardless of server-side streaming — §11) applies identically to `FindByValue`, but an equality predicate's result size can't be known ahead of a scan the way `RangeQuery`'s pre-flight check can (it depends on how many rows actually match, not the queried time range). `FindByValue` instead tracks `total_emitted_bytes` as a running total across the whole query, checked after every match; crossing 2,000,000,000 bytes sets `size_limit_exceeded`, appends a `[WARNING]` `queryStatus`, and stops scanning — so an unselective predicate over a wide range truncates instead of streaming indefinitely past the limit.
- **Schema-growth / missing-file rebuild.** Mirrors zone-map's `InitDB()`-integrated startup rebuild (§4.14) via `XStore::RebuildStaleCatIdxForDb`, called from `InitDB()` after WAL replay, synchronously, before any worker thread can serve a request. A year is flagged stale if: its `.catidx` doesn't exist at all (every pre-existing year in any deployment upgrading to this feature, the first time it runs), can't be read back as a full header, has the wrong magic/version, has `tracked_column_count < desired_tracked_columns` (the same per-DB `columnCount` high-water mark concept zone-map uses, `EffectiveTrackedColumnCount`), or is in the caller's `force_rebuild_years` set (a WAL-replayed year — `ApplyWalRecord`'s `UpdateRow(diff, {})` sets zero new bloom bits for WAL-replayed rows since `catidx_observations` isn't repopulated by `ParseWalRecord`, so the file stays structurally valid but silently under-represents those rows; none of the header-based checks would ever catch this). **A genuine correctness fix mid-implementation, not just structural wiring:** the original design (per the plan) discarded the stale file and let future inserts lazily repopulate the bloom — found during implementation to be a real bloom false-negative bug, since an all-zero bloom entry (what a freshly-recreated file has) returns "definitely absent" for every query value, and historical blocks essentially never receive new inserts, so a lazily-repopulated bloom for old data would in practice never repopulate at all. Fixed with `RebuildOneYearCatIdxBloom`: a synchronous full-row rescan (raw `pread` per row, skip-parse via `ExtractColumnByIndexSkipParse`, `UpdateRow` per row) that unconditionally rebuilds the bloom from real data — mirroring `RebuildOneYearZoneMap`'s own established precedent for the exact same class of problem. Before reopening, the registry is force-evicted for that `(db, year)` key (same registry-staleness fix `RebuildOneYearZoneMap` applies) — otherwise a still-warm in-memory instance from an earlier pass in the same `InitDB()` call would be handed back without ever calling `Open()`, so the freshly-unlinked file would never actually get recreated on disk, and every bit this rebuild sets would live only in that instance's fd to the now-deleted inode — invisible on disk, lost at the next LRU eviction or process exit.
- **Non-static instance methods, not static (a real deviation from the plan's original sketch).** `CompactOneYearCatIdx`/`CompactColdCatIdxForAllDbs` and the rebuild functions are non-static `XStore` instance methods, not static as originally sketched — both need to call the non-static `ExtractColumnByIndexSkipParse`. The compaction background thread constructs and owns its own `XStore compaction_store` instance for its lifetime (§5.2's "one instance per worker thread" convention), since `main.cpp` doesn't call `StartWalWriters` explicitly the way the original plan assumed — it actually runs via `std::call_once` inside `XStore`'s own constructor (`XStore_Management.cpp`).
- **Deferred follow-ons** (per the design spec's own "Deferred follow-ons" section, not part of this feature's scope): a **range-predicate row-retrieval RPC** (reuses existing `.zmap` min/max, no new file format needed); **"unknown column"/any-column value search** (own future design cycle, closer in shape to the deferred `LIKE`/full-text item); **`!=` acceleration** (not meaningfully solvable by either the bloom filter or the bitmap directory — not pursued). Additional real, review-surfaced follow-ons tracked in `TODO.md`: no dedicated test for the WAL-replayed-years rebuild path (mechanical mirror of already-tested zone-map logic, judged low-risk); compaction/rebuild scans are serial across multiple stale years, unlike zone-map's `XStorePreadPool::ParallelFor` fan-out; **the bloom filter's `k`/bytes-per-entry sizing needs real retuning against actual per-block cardinality data** (see the `BloomEntry` note above — currently saturates well before true high cardinality, costing pruning but never correctness); no Mystic benchmark gate yet (no workload tag currently exercises equality-lookup queries).

### 4.16 String pattern search — `FindByPattern` (TEMPORARY IMPLEMENTATION (option A))

`FINDBYPATTERN = 26` (`proto/XStore.proto`) streams every row in `[startTime, endTime]` whose `columnIdx` holds a `stringData`/`bytesData` value matching `pattern`, in the same `UnaryQuery_REP`-entry wire shape as `FindByValue`/`RangeQuery`. Any other `FData` type, a missing column, or an unwritten row never matches (no numeric-to-string coercion). Clients: `XStoreClient::FindByPattern` (C++), `XStoreClient.findByPattern` (Python).

- **Modes (`PatternMode`).** `PATTERN_LIKE`: SQL `LIKE` — `%` any run of bytes, `_` exactly one **byte** (not one UTF-8 code point), `\` escapes the next byte, whole-value match; `caseInsensitive` = ASCII-only fold (`ILIKE`). `PATTERN_REGEX`: RE2, UTF-8, unanchored partial match (`^`/`$` to anchor); `caseInsensitive` = RE2 `case_sensitive=false`.
- **RE2 build dependency.** Fetched and built from source by default (`XSTORE_FETCH_RE2=ON`, pinned `2025-11-05`), against protobuf's already-fetched Abseil — one Abseil per binary. `XSTORE_FETCH_RE2=OFF` uses a system RE2 via pkg-config. With no RE2 (or CMake < 3.22, RE2's minimum) the server still builds and REGEX requests return `[ERROR] ... REGEX mode unavailable: server built without RE2`.
- **Limits.** Pattern ≤ `FIND_BY_PATTERN_MAX_PATTERN_BYTES` (4096). RE2 `max_mem` = `FIND_BY_PATTERN_REGEX_MAX_MEM_BYTES` (8 MiB) — a regex needing more fails to compile. RE2 is linear-time (no ReDoS). Same 2 GB streamed-result guard as `FindByValue`.
- **Implementation — TEMPORARY.** `XStore::FindByPattern` (`src/XStore/XStore_PatternOps.cpp`, kept alone so it can be swapped out) is a brute-force sequential scan: per year segment, read-lock + `madvise(WILLNEED)`, then per row decode the one column via `ExtractColumnByIndexSkipParse` and test it with a per-query `PatternMatcher` (`XStore_PatternMatch.*`). LIKE splits the pattern on `%` into fixed-width segments: first/last checked anchored, middle ones by leftmost fit (`memmem` when a segment has no `_`). **No index and zero write-path cost** — inserts, the WAL apply path, `.zmap` and `.catidx` are untouched. The RPC and client APIs are intended to be permanent; this scan is the baseline for the pending A (scan) vs. B (per-block trigram bloom) vs. C (inverted trigram index) decision tracked in `TODO.md`.
- **A+ raw-bytes prefilter (2026-09-26, still option A — no index).** `PatternMatcher::PrefilterLiteral()` returns the longest run of fixed bytes in a case-sensitive LIKE pattern (`AAPL%` → `AAPL`, `%order-1234%` → `order-1234`; escaped `\%`/`\_` count as fixed). `stringData`/`bytesData` values sit verbatim in a row's serialized bytes, so every matching row contains that literal: the scan runs `memmem` over each year segment's contiguous row span and fully decodes+matches only rows with a hit, then resumes at the next row. No false negatives; false hits (literal in another column, straddling two rows, inside a hole's zero bytes) are rejected by the unchanged full check. Output stays chronological. ILIKE, REGEX and `%`/`_`-only patterns have no literal and use the plain per-row loop. Guarded by `XStorePatternTestFixture.RandomizedResultsEqualPerRowReference` (500 rows incl. holes/unset/int cells and a decoy string column, 300 random LIKE/ILIKE patterns) plus targeted other-column and NUL-over-holes tests.
- **Baseline numbers** (`XStorePerfTest.FindByPatternScanThroughput`, `XSTORE_PERF_N=1000000`, 64-byte rows, one string column like `AAPL-order-123456`; 16 cores, 15 GB RAM, ext4, kernel 6.8.0-142; 2026-09-26). "Cold" = XStore's cached mmap dropped (`EvictMappedFilesUnderPrefixForTests`) + `POSIX_FADV_DONTNEED`; plain `DONTNEED` alone does not evict pages still mapped.

  | Pattern | Cold | Warm | Warm rows/s |
  |---|---|---|---|
  | LIKE `AAPL%` | 0.26 s | 0.22 s | 4.6 M |
  | LIKE `%99` | 0.24 s | 0.19 s | 5.2 M |
  | LIKE `%order-1234%` | 0.27 s | 0.22 s | 4.5 M |
  | LIKE no-match `%ZZZZ%` | 0.27 s | 0.22 s | 4.6 M |
  | ILIKE `%aapl%` | 0.30 s | 0.26 s | 3.9 M |
  | REGEX `^(AAPL\|MSFT)-order-[0-9]+7$` | 0.44 s | 0.39 s | 2.5 M |

  Scan cost is dominated by row decode, not matching (a no-match scan costs the same as a 125k-match one), so only skipping rows/blocks can beat it — A+ below does that on raw bytes without an index; B or C would do it with one; REGEX ≈ 1.8× LIKE. Cold is only 13–26% slower here because 64 MB fits a fast disk's readahead — data far larger than RAM is where B's block pruning would matter most.
- **A+ numbers** (same test and data, 2026-09-26, **machine under heavy unrelated load** — load average up to ~70 on 16 cores; the unchanged ILIKE/REGEX paths read 35–50% slower than their baseline above, so treat absolute values as inflated). Result bytes are identical to A for every pattern.

  | Pattern | Literal present in | A warm | A+ warm (2 runs) | A+ cold |
  |---|---|---|---|---|
  | `AAPL%` | 1 in 8 rows | 0.22 s | 0.10 / 0.09 s | 0.14 s |
  | `%99` | ~5% of rows | 0.19 s | 0.06 / 0.06 s | 0.11 s |
  | `%order-1234%` | 111 rows | 0.22 s | 0.01 / 0.01 s (~70 M rows/s) | 0.06 s |
  | `%ZZZZ%` | no rows | 0.22 s | 0.02 / 0.02 s (~42 M rows/s) | 0.08 s |
  | `%order%` | every row (and every row matches: 41.9 MB reply) | not measured | 0.55 / 0.49 s | 0.65 s |

  Selective literals become memory-bandwidth-bound (one SIMD `memmem` sweep of the 64 MB span + a handful of decodes) instead of decode-bound. When the literal is in (nearly) every row the prefilter cannot skip anything and adds one `memmem` call per row on top of A's work; its size is unknown until a fair A-vs-A+ run on a quiet machine (tracked in `TODO.md`), and an adaptive fallback (switch to the plain loop once hits exceed ~25% of scanned rows) is the proposed remedy if it matters.
- **Memory (measured on a live server, 2026-09-26).** No growth: server heap flat across 9,000+ mixed LIKE/ILIKE/REGEX queries and repeated big-result rounds (one-time +11 MiB allocator warm-up, then constant). Per query: 0 extra for scans with no matches, ~proportional to result size otherwise (~8 MB result → +7 MiB), capped at ≈ 2 × `STREAMED_QUERY_CHUNK_SIZE_BYTES` (64 MiB buffer + ZMQ's copy while sending ≈ +128 MiB for a 75 MB result), released when the query ends. This ceiling is shared with `RangeQuery`/`FindByValue`/`BatchQuery` (same streaming path) — see TODO.md for lowering it.

### 4.17 Insert-path memory, index-observation sizing, and index width growth (2026-09-26)

**Problem (measured).** After bulk inserts the server kept its peak heap: 3.8 MiB idle → 624 MiB RssAnon after 700k `BatchInsert` rows in 20k-row batches (4 workers). This was not unbounded growth — it tracked the largest requests, not total rows — but it contradicted the low-footprint goal and competes with the page cache that serves mmap'd data. `gdb` + glibc `malloc_stats()` separated three stacked causes:

1. **WAL writer pinned applied records.** `WalWriterLoop` reuses `std::vector<WalRecord> batch(WAL_BATCH_MAX_RECORDS)`; slots were never reset after apply, so each shard kept its last records (rows + observations) alive until a later dequeue overwrote them — ~100 MB per 20k-row record, one per active shard (worst case 256 records × 8 shards). **Fix:** `batch[i] = WalRecord{}` for every processed slot at the end of each writer iteration, *after* all completions are signalled — same destructor work as before (a later move-assignment used to do it), moved off the SYNC callers' latency path. Release trails the SYNC ack by a few ms by design.
2. **Per-row observations were padded to the tracked width.** Every row built one zone-map and one catidx observation per tracked column (≥ 64 — `EffectiveTrackedColumnCount` floor), even for a 1-column row: ~5 KB per 128-byte row, so a 2.26 MB request became ~108 MB. **Fix:** observations are built only for columns `[0, min(fielddata_size, tracked))` (catidx additionally omits unset columns, which `CatIdxFile::UpdateRow` always skipped). `WalRow::zone_map_pad_to` + a required `pad_to` parameter on `ZoneMapFile::UpdateRow` bump `null_count` for columns `[observations.size(), min(pad_to, file width))` — bit-identical index contents (pinned by `XStoreMemoryTest.MixedRowsIndexSemanticsArePinned`, mixed widths/types/unset/strings). Rows replayed from the WAL keep `zone_map_pad_to = 0` (they carry no observations and still cause no index update; their years are rebuilt at `InitDB`).
3. **glibc retention** of the freed transient memory — shrinks with (2).

**Index width growth (schema-free rows).** Index files are created at least 64 columns wide; a DB's tracked width (`ConfigStruct.columnCount` — *not* `rowLength`, which is fixed and still rejects oversized rows) grows up to `MAX_TRACKED_COLUMN_COUNT` = 4096 when wider rows arrive. Two fixes:
- **Width before first write:** each insert computes the request's widest *accepted* row once (rows whose serialized size exceeds `rowLength` are skipped — they are rejected later and must never grow the persisted, high-water `columnCount`), calls `MaybeGrowColumnCount` once (replacing the old per-row calls), and uses `max(EffectiveTrackedColumnCount, widest)` for its records — so a fresh DB whose first batch has 128 columns gets 128-wide `.zmap`/`.catidx` immediately (previously 64 until a restart). Seeding `CreateDB_REQ.columnCount` remains the explicit option for known-wide datasets.
- **Full-scan notice:** existing year files keep their width while the server runs (widening a live file would discard its stats); a query on a column ≥ that file's width is still answered correctly by full scan, and MIN/MAX/SUM/AVG/VARIANCE/STDDEV/EXISTS/OHLC/`FindByValue` now add `[WARNING] [<OP>] [DB: X] - column <c> is not yet indexed in <year> (index width <w>); answered by full scan -- restart XStore to rebuild the index` to their status; `MaybeGrowColumnCount` logs one warning when the width grows. **Status format:** the notice is appended to an op's existing status with `" | "` (e.g. `SUCCESS | [WARNING] ...`), and `FindByValue` now appends every warning instead of keeping only the last — clients should test statuses by prefix/`find("SUCCESS")`, not exact equality. For `FindByValue` the notice follows the `.zmap` width as a proxy for `.catidx`'s; in width-mismatch states it can be spurious or missing, but results stay correct (real-scan fallback). The check costs nothing for columns < 64 (every file is ≥ 64 wide) and uses an in-memory registry peek (`PeekOpenZoneMapWidth`) before any header read for wider columns.

**Results** (interleaved baseline-vs-new, 5 rounds, load average 1.1–2.6; 16 cores): BatchInsert 175k → **860k rows/s (~4.9×)**, RangeInsert 176k → **1.03M rows/s (~5.8×)**, UnaryInsert (SYNC, fsync-bound) unchanged. Heap after 700k rows: RssAnon **624 → 89 MB**, glibc in-use 346 → 47 MB (remaining: per-worker request arenas ~5 MB each + index/file caches).

**Allocator comparison** (`LD_PRELOAD`, no code change; medians vs glibc): mimalloc 3.5.3 +12–30% throughput but **+60% resident memory** (143 vs 89 MB; 23 MB idle); **jemalloc 5.4.0 +7–19% throughput at ~equal memory** (92 MB); all three pass the full suite. **Integrated 2026-09-27** (plan `docs/superpowers/plans/2026-09-27-jemalloc-integration.md`). Tuning chosen by measurement: `background_thread:true` (vs default and a fast-decay variant) — best insert throughput and memory below glibc. Gate on the real linked builds (5 interleaved rounds, load 0.3–1.2): BatchInsert 0.85M → **1.06M rows/s (+24%)**, RangeInsert 1.00M → **1.17M (+16%)**, FindByPattern LIKE +11%, REGEX +14%; server RssAnon after 700k rows: glibc 89 MB flat vs jemalloc **65 MB at +5 s, 50 MB at +30 s** (background purge); idle 4.1 → 6.5 MB. Net effect of §4.17 + jemalloc on this workload: ~624 MB → ~50 MB resident, BatchInsert 175k → 1.06M rows/s. **Speed sweep (2026-09-27, `MALLOC_CONF` on the linked binary, interleaved):** `percpu_arena:percpu`, `narenas:16`, `tcache_max:128K`, `dirty_decay_ms:30000`, `metadata_thp:auto` — all neutral or slower. **`thp:always` (heap on transparent huge pages): BatchInsert +23%, RangeInsert +45%**; per-call query latency unchanged (server probe: UnaryQuery p50 0.376 → 0.367 ms, p99 0.544 → 0.529; RangeQuery 10k rows p99 5.99 → 5.14 ms; MIN over 700k rows and FindByPattern unchanged); one higher single worst-case (UnaryQuery max 2.2 → 6.1 ms of 3,000 calls), consistent with occasional THP handling stalls. **Memory cost ≈ 2× and bounded:** idle 5 → 32 MB; after three 700k-row loads + idle, 60 MB flat vs 95–125 MB oscillating (khugepaged collapsing partly-used regions vs jemalloc purge splitting them; capped by jemalloc's mapped heap, not unbounded). Adopted as the default (`XSTORE_JEMALLOC_THP=ON`); set it OFF for memory-constrained deployments.

### 4.18 Index crash-consistency — dirty-flag protocol & graceful shutdown (2026-10)

**Problem.** `.zmap` and `.catidx` writes are write-through `pwrite()`s with no fsync (§4.14, §4.15), and so are the `.XSTORE` data writes. A **process** crash is already safe: the page cache survives, and a mid-apply crash is replayed from the WAL and its year's indexes rebuilt. An **OS crash or power loss** is not: the kernel may persist the index pages but not the data pages (or the reverse), leaving `.zmap`/`.catidx` disagreeing with the data — wrong MIN/MAX/SUM pushdown, or bloom false negatives that silently drop `FindByValue` matches. Before this change nothing at startup could detect that (`ZoneMapNeedsRebuild` checked magic/version/width only). Plan: `docs/superpowers/plans/2026-09-28-durability-a-dirty-index-rebuild.md` (commits `1f1e1959..a28af4cd`).

- **Header format change.** `ZoneMapFileHeader` gains `uint32_t dirty` in the former padding slot at offset 12 (size stays 24 B; `static_assert(sizeof == 24)`, `offsetof(dirty) == 12`), `ZONE_MAP_VERSION` 3 → 4. `CatIdxFileHeader` gains `uint32_t dirty` + `uint32_t reserved` at the end (24 → 32 B, 8-byte aligned, `static_assert(sizeof == 32)`), `CATIDX_VERSION` 1 → 2. Upgrades use the existing version-mismatch discard-and-rebuild path (§4.14): **one full rebuild of every year on the first start after upgrading**, then the files are v4/v2.
- **Mark dirty once per session.** `ZoneMapFile` and `CatIdxFile` each keep `bool dirty_on_disk_` (initialised from the header on `Open()`). Every method that writes index content first calls the private inline `EnsureDirtyOnDisk()` (`if (!dirty_on_disk_) MarkDirtyOnDisk();`), under the file's existing mutex: set `header_.dirty = 1`, `pwrite` the header, `fdatasync`, then `dirty_on_disk_ = true`. Covered write paths: `ZoneMapFile::UpdateRow`; `CatIdxFile::FlushBlock` (the bitmap-section invalidation header write, the bloom-block write and the `block_count` header write all follow the single `EnsureDirtyOnDisk()` at its top, so those header writes carry `dirty = 1`) and `CatIdxFile::AppendBitmapSection` (compaction data + commit header). Open-time creation of a fresh/discarded file (`WriteFreshHeader`) writes `dirty = 0` deliberately — nothing stale to protect, and no row has been folded in yet. **If the mark's `pwrite`/`fdatasync` fails**, it logs an error and the write proceeds anyway (failing inserts would be worse); the file stays unmarked and the next write retries. Hot-path cost: one predictable branch per index write plus one header `fdatasync` per index file per session; no new per-row or per-query syscalls.
- **Mark clean — order matters.** `bool MarkClean()` (`[[nodiscard]]`): `fdatasync(fd_)` (index content), then `header_.dirty = 0`, header `pwrite`, `fdatasync`, `dirty_on_disk_ = false`; any failure returns false and leaves the file dirty. **The caller must `fdatasync` the matching `.XSTORE` data file first** — a clean index over unsynced data is exactly the inconsistency being prevented. `MarkClean` never touches the data file itself.
- **Startup.** `ZoneMapNeedsRebuild` returns true for `header.dirty != 0` (after the magic/version/width checks, no extra I/O); `RebuildStaleCatIdxForDb` treats `dirty != 0` like a stale width. Both log `[INFO] ... <year>.zmap|.catidx marked dirty (unclean shutdown) -- rebuilding`. The rebuild (`RebuildOneYearZoneMap` / `RebuildOneYearCatIdxBloom`) finishes by `fdatasync`ing the data file and then calling `MarkClean()` on the freshly rebuilt index — but only if the scan completed (a short read marks it incomplete). Any failure there (incomplete scan, data `fdatasync`, `MarkClean`) logs an error and leaves the index dirty, so the next start rebuilds again. A year with no rows keeps its fresh `dirty = 0` header. WAL-forced rebuilds (`force_rebuild_years`) go through the same function and also end clean.
- **Registry eviction caveat.** The LRU cap on the zone-map/catidx registries (§4.14/§4.15) can evict a file that was dirtied this session. Eviction adds no fsync (hot path), so an evicted dirty index **stays dirty** on disk even across a clean shutdown (`Shutdown()` only sees registry-open files) and is rebuilt on the next start. Accepted cost: a bounded rebuild, never a wrong answer.
- **`XStore::Shutdown()`** (static; `src/XStore/XStore_Wal.cpp`), in order: (1) `shutdown_flag_.exchange(true)` — a second call returns immediately (idempotent); from here `UnaryInsert`/`BatchInsert`/`RangeInsert` return an `[ERROR] ... Server has shut down; insert rejected` status and `EnqueueWalRecord` refuses (so a SYNC waiter cannot block on joined writers); (2) `StopWalWriters()`: stop and join the WAL writers, then `Checkpointer::StopAfterFinalCycle()` — join the checkpointer thread and run one final cycle that `fdatasync`s (by path, throwaway fd) every data file dirtied since the previous cycle (hole-punch deletes included: they are noted dirty too), `fsync`s their directories and advances every ring's checkpoint to its **applied** LSN (which equals head except after a writer exception between `CommitAppended` and `PublishApplied`) (§4.19); (3) **gate:** only if the final cycle succeeded and the checkpointer was never poisoned (`FinalCycleOk() && !Poisoned()`), otherwise log `[SHUTDOWN] - indexes left dirty ...` and return with every index dirty (the next start rebuilds); (4) `MarkClean()` every zone-map and catidx registry entry. The gate is the cycle's outcome, not membership of each file in the last cycle's synced set (a file synced by an earlier cycle is legitimately absent from it), and `Shutdown()` syncs nothing itself: the former fd-cache `fdatasync` loop and the throwaway-fd re-sync were removed because a fresh fd would not see an earlier writeback error. **Precondition:** callers must have stopped serving requests (a racing inline-mode insert could leave a clean index over an unsynced row). Locking: the registry mutex is held only around the `MarkClean()` calls (it also pins entries against eviction); order is registry mutex → file mutex, and no file method takes a registry mutex. A write racing in after `MarkClean` just re-marks the file dirty.
- **WAL checkpoint at clean shutdown.** Without it a clean stop would still replay the un-checkpointed tail of each ring next start and force-rebuild every year it touched (§4.12). The checkpointer's final cycle (step 2 above; replaces the earlier `XStore::CheckpointWals`, which re-parsed every shard file, synced the referenced data files and invalidated the shard header, and is removed together with `RegisterDataStoreDir`, `InvalidateWalFileHeader` and `ReclaimWalFileSize`) does this from the dirty-range set instead of re-reading the log. Any failure — a file that cannot be synced, a poisoned checkpointer, a header write that did not stick — leaves that ring's checkpoint behind, so the next start replays and rebuilds as before. Measured SIGTERM stop after 700k SYNC rows: 1.43 s before, 0.28 s after (§4.19).
- **Graceful server shutdown sequence** (`src/main.cpp`, `ZmqServer`, `XStore_Curve.cpp`):
  1. `main` blocks SIGINT/SIGTERM with `pthread_sigmask` as its first statement, so every later thread (spdlog, ZMQ I/O threads, WAL writers, stats) inherits the mask and no default handler can kill the process with indexes dirty.
  2. `ZmqServer` is constructed early (before the slow `InitDB`/WAL-replay boot) and one detached thread `sigwait`s. First signal: log, then `ZmqServer::RequestStop()` (`zmq_ctx_shutdown`, valid before `StartServer` — a signal during boot is remembered and acted on once boot finishes). **Second signal: flush the log and `_exit(1)`**, leaving the dirty flags set (safe; the next start rebuilds). A mutex-guarded `g_server` pointer, nulled after `StartServer` returns, keeps a late signal from touching a destroyed server.
  3. `zmq::proxy` returns on ETERM; worker `recv` calls (and a reply `send` in flight) throw/return ETERM and each worker leaves its loop (`WorkerRoutine` catches ETERM; the generic handler rethrows it so no spurious "handler threw" is logged). `XStoreZapHandler::Loop` also catches ETERM. Client-facing and worker sockets get explicit linger values so context teardown cannot block on an unread client.
  4. `StartServer` returns `bool`: it waits up to `ZMQ_SHUTDOWN_DRAIN_TIMEOUT_S` (10 s) on a worker-exit latch (mutex + cv + counter in a `shared_ptr`, since the workers are detached and their final decrement can outlive the `ZmqServer`) for every worker to finish.
  5. Drained: `main` calls `StopCatIdxCompactionThread()` (so compaction cannot re-dirty an index), then `Shutdown()`, logs, returns 0 (atexit hooks then stop the stats thread and the already-stopped WAL writers).
  6. **Deviation from the original design text (plan DD7):** the plan said to proceed to `Shutdown()` after the bounded wait. If workers fail to drain within 10 s, `main` instead `_exit(1)`s **without** calling `Shutdown()`: `Shutdown()` requires a quiescent server, so running it beside a live worker could mark an index clean over an in-flight write. The indexes simply stay dirty and the next start rebuilds.
- **Compaction stop check.** `CompactOneYearCatIdx` checks `catidx_compaction_stop_flag_` every 64K rows and abandons the year (nothing appended; retried next start). Found by test: a restart's background compaction of a cold 31.5M-row year otherwise delayed `StopCatIdxCompactionThread()` by 10+ s, defeating the shutdown window.
- **jemalloc note.** The jemalloc background thread (`background_thread:true`, §4.17) already exists before `main` runs, so "block signals before any thread exists" is not literally true. It is safe because jemalloc blocks all signals in its own threads, so they never consume SIGINT/SIGTERM.

**Measured costs.** One box, running other load (load1 ~1.3–1.9), interleaved A/B, so **indicative, not authoritative**. Baseline = the pre-durability perf binary at `3faee522`, which already has jemalloc, so the comparison isolates Durability A's cost (not the allocator's).

| Workload | Result vs. pre-durability |
|---|---|
| BatchInsert, 200k rows | −2.2 % (5 rounds); −7.9 % (7 rounds, new-first order) |
| BatchInsert, 1M rows | −0.7 % median (3 rounds) |
| RangeInsert, 200k rows | −4.7 % / −3.3 % (noisy) |

The insert deficit shrinks as the run lengthens (−7.9 % at ~0.15 s runs → −0.7 % at 1M rows), which points to a **fixed once-per-session cost** (two header `fdatasync`s per index file) rather than a per-row cost. That reading is inferred from the scaling, not timed directly. No per-row regression was found. Restart after 700k SYNC rows (one year): **SIGTERM** stop 5.5 s (exit 0; measured before the WAL ring, 0.28 s after it, §4.19), restart to first MIN query **0.15 s**, no rebuild and no WAL replay; **SIGKILL** restart to first MIN query **62 s** (the year is rebuilt — both the leftover WAL batch and the dirty flag trigger a rebuild; MIN correct).

**Scope limits.**
- Durability A fixes **index-vs-data consistency only**. Loss of acknowledged SYNC writes on power loss was closed afterwards by the WAL ring + paced checkpoint (§4.19), subject to the residual risks listed there.
- ASYNC records still queued in the WAL writers at stop are dropped, as before (the writer loop exits on its stop flag without draining).
- A SYNC insert in flight at signal time may be durable on disk but never acknowledged (its reply send fails with ETERM; the client times out).
- A signal during a long boot-time rebuild is acted on only after boot finishes; a second signal exits immediately.
- Tests: `DurabilityHeaderLayoutTest`, `DurabilityMarkDirtyTest`, `DurabilityRebuildTest`, `DurabilityShutdownTest` (`tests/integration/XStoreDurabilityTest.cpp`) and `XStoreGracefulShutdownTest` (`tests/integration/XStoreGracefulShutdownTest.cpp`, in `xstore_network_tests`; forks the real binary: SIGTERM/SIGINT leave all indexes clean and the restart logs no rebuild/replay, SIGKILL leaves them dirty and the restart rebuilds). Untested: the failure branches of rebuild completion, the drain-timeout `_exit(1)` and the second-signal `_exit(1)` (need fault injection / a held worker).

### 4.19 WAL ring + paced checkpoint (Durability C, 2026-10)

**Problem.** Before this change an acknowledged SYNC insert was (a) `fdatasync`ed in the WAL and (b) `pwrite`n into the `.XSTORE` page cache; the data file was never fsynced and the next batch overwrote the shard's WAL from offset 0. Once that happened the earlier batch's only copy was unsynced data-file pages, so an OS crash or power loss within the kernel's writeback delay (seconds to ~30 s) lost acknowledged writes. Process crashes were already safe (the page cache survives). Goal: **an acknowledged SYNC write survives power loss**, without a data fsync per commit. Spec `docs/superpowers/specs/2026-10-02-wal-ring-checkpoint-design.md`, plan `docs/superpowers/plans/2026-10-02-wal-ring-checkpoint.md`. Commits `ff7728d3` (record v2 + ring file), `f2a2e4a5` (writer appends to the ring), `f5e5ceff` (dirty tracking), `ba37db98` (checkpointer), `b4d7cf92` (replay from the checkpoint + legacy upgrade), `48ab2a50` (shutdown final cycle), `dbd6026c` (direct path), `5c9fcc69` (crash-simulation tests), `ab41c638` (test ring-size override); plus `46428658`, an unrelated pre-existing `XStorePreadPool` use-after-destruction at `exit()` that the new tests exposed (the pool's function-local static queue is now heap-allocated and leaked).

**Invariant.** For every data-file write, either its WAL record is still inside the live ring, or a data sync that *started after the write finished* has completed. A ring slot is reused only when the second holds. Everything below exists to keep that true cheaply.

- **Ring file** (`include/XStore/XStore_WalRing.h`, `src/XStore/XStore_WalRing.cpp`; `DataStore/WAL/shard_<N>.WAL`, same path as before). A 4096-byte header region holds two 512-byte slots (`RingHeader`, 48 B: magic `XRNG`, version 1, `shard_id`, `ring_bytes`, `checkpoint_lsn`, `slot_seq`, CRC32C); a write goes to slot `slot_seq % 2` followed by `fdatasync`, and the valid header is the CRC-good slot with the highest `slot_seq`, so a torn header write cannot lose the checkpoint. The ring follows: `ring_bytes` of log addressed by LSN (a byte position in the never-wrapping logical log): file offset = `4096 + lsn % ring_bytes`; space in use = `head_lsn − checkpoint_lsn`. Default `WAL_RING_BYTES` = **64 MiB per shard** (the old file was a 512 MiB preallocation). `InitRingFile` `posix_fallocate`s, writes the ring as zeros in 4 MiB chunks (so extents are written, not unwritten, and a later append never changes file metadata), `fsync`s, **then** writes the first header slot — a header is never durable before the ring it describes; `GetOrOpenRing` then fsyncs the WAL directory so the new file's entry survives. Replay reads `ring_bytes` from the header, not from the tunable, so changing `WAL_RING_BYTES` affects only newly created files. Test binaries default to an 8 MiB ring (`tests/integration/XStoreTestSupport.h`, otherwise each test process pays ~1 s zero-filling eight 64 MiB rings); `XSTORE_TEST_RING_BYTES=<decimal bytes>` overrides it, and the perf runs must set it to production size (see Measured behaviour).
- **Record format v2.** `[u32 recordLen][u32 crc32c][u64 lsn][u16 dbNameLen][u16 rowLength][i32 timeResolution][u32 rowCount][dbName][epochTime + row bytes]...`; `recordLen` counts the bytes after itself, and the **CRC covers everything after itself, the LSN included** (`RECORD_FIXED_BYTES` = 28). Replay accepts a record only if its LSN equals the LSN it expects at that position, which rejects bytes left by the previous lap (LSN smaller by `ring_bytes`). A record **never straddles the ring end** (`PlanAppend`): when it would, the writer first writes a **PAD record** (`dbNameLen` = `0xFFFF`) covering the remainder; if fewer than `RECORD_FIXED_BYTES` bytes remain, nothing is written and replay skips them by the same rule.
- **Writer path** (`WalWriterLoop`, `src/XStore/XStore_Wal.cpp`). Group commit, gather window, CRC32C and `pwritev` are unchanged. Per gathered batch, a maximal run of ring-bound records forms a sub-batch of at most `ring_bytes/4` per ring (a lone larger record still forms its own). `Ring::Reserve` finds the append position and blocks until the bytes fit below `WAL_STALL_FILL` (90 %) of the ring or the ring is empty, for at most `WAL_STALL_TIMEOUT_MS` (5 s). On timeout the sub-batch is failed ("ring full ... failing the batch (overloaded)" appears only in the server log; clients see the generic enqueue/insert failure, never the word "overloaded") and nothing is overwritten: SYNC callers get a failure, ASYNC callers (already acknowledged) lose the record. Then: `pwritev` into the ring, **one `fdatasync` of the ring file per sub-batch**, `CommitAppended` (head moves) and only then `ApplyWalRecord` to the data files; `PublishApplied` advances `applied_lsn` and the callers are released. A record is applied only if its ring bytes are durable. If the ring write or sync fails, head does not advance and the writer overwrites the range with zeros (best effort, plus `fdatasync`) so its CRC-valid bytes cannot be matched by a later, shorter record; a *real* ring `pwritev`/`fdatasync` error (anything but `EINTR`/`EAGAIN`) additionally **poisons** the checkpointer (below). A single-row record larger than half the ring fails (`kFail`); only a test-sized ring can trigger this.
- **Dirty tracking.** `ApplyWalRecord` is the single choke point for `.XSTORE` row writes (ring, direct, BYPASS and replay all go through it); after each coalesced `pwrite` run it calls `walring::Dirty().Note(ring, file, begin, end, ring_lsn_end)`. `DirtyTracker` keeps merged byte ranges per file plus, per `Ring`, the end LSN of the last ring record that touched the file (`ring == nullptr` for direct/BYPASS/replay writes). A missing *range* only makes a sync heavier; a missing *file* would be a durability hole, and a test (`WalCrashSimTest.EveryInsertApiMarksItsFileDirty`) asserts that every insert API notes its file.
- **Checkpointer** (`include/XStore/XStore_WalCheckpoint.h`, `src/XStore/XStore_WalCheckpoint.cpp`). One leaked-singleton thread per process, started by `StartWalWriters` after the writers, handling every ring. A **cycle** (`RunCycle`, under one cycle mutex): (1) snapshot every ring's `AppliedLsn()`; (2) only then `Dirty().Take()` the dirty files into the carried set; (3) `fdatasync` each file **by path** (a throwaway fd, so an fd-cache eviction cannot hide a file; `ENOENT` means a deleted DB and is skipped); (4) `fsync` each file's parent directory (a new year file's directory entry is not made durable by syncing the file); (5) only if 3 and 4 fully succeeded, `AdvanceCheckpoint(snapshot)` per ring (header write to the alternate slot + `fdatasync`) and wake stalled writers. Snapshot-before-Take is what makes it safe: every apply below the snapshot had finished and noted its file before the Take, and records applied after the snapshot are covered by the next cycle. A failed data or directory sync keeps the carried set and advances nothing; a ring-header write that fails for one ring does not stop the other rings from advancing (conservative: each ring's checkpoint is independent), and a *real* header error poisons (below).

  The policy is lazy so that bursts that fit in the ring pay almost nothing. The loop ticks every 1 ms; "fill" is the maximum over all rings.

  | Condition | Action |
  |---|---|
  | fill < 25 % (`WAL_CKPT_SOFT_FILL`) | no paced flushing |
  | fill ≥ 25 % | one paced step per tick: `sync_file_range(WAIT_BEFORE\|WRITE\|WAIT_AFTER)` over the first not-yet-flushed gap of the dirty ranges, ≤ `WAL_FLUSH_CHUNK_BYTES` (4 MiB) |
  | oldest unsynced dirty range ≥ `WAL_CKPT_MAX_AGE_MS` (5 s), at any fill | full cycle |
  | dirty or un-checkpointed data and no writer batch for ≥ `WAL_CKPT_IDLE_MS` (50 ms) | full cycle |
  | fill ≥ 50 % (`WAL_CKPT_CYCLE_FILL`) | back-to-back cycles while they make progress; warning at most once per 60 s |
  | previous cycle failed (not poisoned) | retry after a 50 ms back-off |
  | fill ≥ 90 % (`WAL_STALL_FILL`) | writers stall in `Reserve`, then fail as "overloaded" after 5 s |

  The idle trigger keys off the start of the writer's last gathered batch (one relaxed store per batch). Operators can change the two time triggers with `XSTORE_CKPT_IDLE_MS` and `XSTORE_CKPT_MAX_AGE_MS` (`src/main.cpp`): digits only, unsigned, `0` or unset = the tunable default; an invalid value is logged as a warning and ignored; the effective value is logged at startup as `[CONFIG]`. A graceful stop runs its final cycle regardless.
- **Sticky sync errors ("poison", the fsyncgate rule).** After a genuine writeback error Linux may mark the lost pages clean, so a *retried* `fdatasync` can return 0 without the data being on disk; advancing the checkpoint on such a retry would discard the only copy. Therefore the first real error from `fdatasync` of a data file, `fsync` of a directory, the ring **header** write (`pwrite`/`fdatasync` of a header slot, in the checkpointer or in the replay commit — a failed replay commit also fences the shard), the WAL **writer's own ring** `pwritev`/`fdatasync` (the batch also fails to its callers), or `sync_file_range` (**any** errno except `EINTR`/`EAGAIN`, retried in place, and `EINVAL`/`ESPIPE`/`ENOSYS`/`EBADF`, "unsupported here", skipped as best effort — `sync_file_range` consumes any writeback error) **poisons** the checkpointer for the life of the process. The ring therefore holds **two independent open file descriptions** of its file (two `open()` calls, not `dup()`): one for the writer's records, one for header writes. Linux reports a writeback error once per open file description, to whichever `fdatasync` runs first, so with a shared description the checkpointer's header sync could swallow the error of the writer's ring pages (the batch would be acknowledged although its pages were dropped) or the writer could consume a header-page error (memory ahead of disk). Operationally, once `[WAL CKPT] - CHECKPOINTER POISONED` is logged at critical level: no ring's `checkpoint_lsn` advances again; the checkpointer stops cycling; the rings fill, writers stall at 90 % and then fail callers (the log says "overloaded"; clients see the generic insert failure); the direct path refuses; `Shutdown()` leaves every index dirty. Reads and already-applied data are unaffected. Nothing recovers it at runtime: **restart the server**, which replays everything since the last good checkpoint. Not poisoning (retryable): failure to `open()` a file other than `ENOENT` (e.g. `EACCES`) and test-injected failures. Directory `fsync` failing with `EINVAL`/`ENOTSUP`/`EOPNOTSUPP`/`EROFS` means the filesystem cannot fsync directories at all; that logs one warning per process and neither poisons nor fails the cycle (new-file directory entries just cannot be made durable there). The allowlist covers directory fsync only, not data-file fsync.
- **Direct path for large records.** A multi-row record (single-row records never go direct) with payload `rows × (8 + rowLength)` ≥ `WAL_DIRECT_MIN_BYTES` (1 MiB), or ≥ `WAL_DIRECT_PRESSURE_MIN_BYTES` (64 KiB) while any ring is ≥ 50 % full, is applied straight to its data file with **no ring record**: the writer applies all records of a run, `fdatasync`s each distinct data file once by path and fsyncs its parent directory (`Checkpointer::SyncPathsForReplay`, same fault hooks and poison rule), and only then acknowledges. SYNC and ASYNC both qualify; BYPASS never reaches the writer. **Ordering rule:** it goes direct only if `Dirty().RingClear(file)` — no un-checkpointed ring record touched that file — and no WAL file is fenced (`walring::AnyFenced()`); otherwise a later direct overwrite of timestamp T could be undone after a crash by replaying an older ring record for T. A record that qualifies but is not ring-clear takes the ring route; one larger than half the ring that is not clear makes the writer run checkpoint cycles (2 ms apart) until the file is clear, bounded by the 5 s stall timeout and abandoned on shutdown or poison, then goes direct, or fails as "overloaded". The direct path **refuses** (fails the record) when the checkpointer is poisoned, and fails it if the data or directory sync fails; the rows are already in the file at that point (as for BYPASS) and stay in the dirty set. A crash during a direct write can leave a prefix of an *unacknowledged* batch's rows in the file: all-or-nothing atomicity for unacknowledged large batches is deliberately given up (inserts overwrite by timestamp, so a retry converges). The guarantee is "every ring record acknowledged before the direct record was submitted is already noted on its file"; concurrent unacknowledged writes to the same row have no defined order.
- **Replay** (`XStore::ReplayWal` → `ReplayRingShard`, `src/XStore/XStore_Management.cpp`; runs at `InitDB()`, shards in index order, each starting unfenced). The scan starts at the header's `checkpoint_lsn` and stops at the first of: zero record length; a length over `WAL_REPLAY_MAX_RECORD_BYTES` or impossible; a CRC/LSN/structure failure; one lap. PAD records are stepped over, valid records go to `ApplyWalRecord`. Then, in this order: (1) `SyncPathsForReplay` on every touched data file and its directory (a failure fences the shard); (2) only if the stop was a **corrupt end**, zero the ring from the damaged record to the end of the lap — everything behind the first 4 bytes, `fdatasync`, then the length field, `fdatasync` — so unacknowledged leftovers cannot match a later LSN; (3) `Ring::CommitReplay(end_lsn)`: write the new `checkpoint_lsn` to the alternate header slot and raise head/applied/checkpoint monotonically. A crash during replay simply replays again (applies are idempotent). *Corrupt end* means a damaged record whose unchecked LSN field (bytes 8..15) equals the expected LSN; zeros, a CRC-valid record carrying another LSN, and damaged-looking bytes with a non-matching LSN field are a clean end and are never zeroed (that would cost a ring write per shard on every start once the ring has lapped). **Every failed exit fences the shard**: stat/open failure, read error, apply failure for a DB that still exists, data/directory sync failure, zeroing failure, no matching ring, `CommitReplay` failure. A fenced file is never appended to or wiped: `GetOrOpenRing` returns `nullptr` for it, the writer fails inserts to that shard loudly, and `AnyFenced()` disables the direct path for the whole process until a later replay of the file succeeds or the process restarts. An apply failure counts as "DB deleted" only if the filesystem positively reports the DB directory or its `.CFG` missing (`DbStillExists`: `ENOENT`/`ENOTDIR`); `EACCES`, `EIO` and the like mean "cannot tell" and fence. `ReplayedYearMap` still forces a zone-map/catidx rebuild of every (db, year) touched by replayed records (§4.18); now only records since the last checkpoint count, and after a graceful stop none do.
- **Legacy WAL upgrade.** A non-empty shard file without a ring header is a pre-ring WAL: `ReplayLegacyShard` replays it once with the old streaming parser, `SyncPathsForReplay`s the touched data files, and only then `ftruncate`s it and `InitRingFile`s it with the default ring size (a crash in between leaves a blank file that replays as nothing). A read error, an apply failure for an existing DB, or a failed data sync leaves the file legacy and fences the shard, so inserts to it fail until the next start retries. A file that parses to nothing but is not blank (first `u32` non-zero, or a ring magic in either header slot) is either a ring with **both** header slots damaged or a legacy WAL whose first record was torn: it is fenced, never wiped, until an operator inspects it and removes it. There is no downgrade path: an old binary cannot read a ring file.
- **Shutdown.** `StopWalWriters()` (called by `Shutdown()` and by the `atexit` hook) joins the writers, then `Checkpointer::StopAfterFinalCycle()` joins the checkpointer thread and runs one last cycle that syncs every file dirtied since the previous cycle and advances every ring to its head. `Shutdown()` marks the indexes clean only if that final cycle succeeded **and** the checkpointer was never poisoned (§4.18); it re-syncs nothing itself, because a fresh fd would not see an earlier writeback error. Not gated on per-path membership in the last cycle's synced set: files synced by earlier cycles are legitimately absent from it.

**Tunables** (`include/XStore/XStore_Tunables.h`; `WAL_FILE_PREALLOC_BYTES` and the `WAL_MAX_*` oversized-file tunables are gone).

| Tunable | Value | Meaning |
|---|---|---|
| `WAL_RING_BYTES` | 64 MiB | ring size per shard (new files only) |
| `WAL_DIRECT_MIN_BYTES` | 1 MiB | payload at/above which a multi-row record may go direct |
| `WAL_DIRECT_PRESSURE_MIN_BYTES` | 64 KiB | same, while any ring is ≥ `WAL_CKPT_CYCLE_FILL` full |
| `WAL_CKPT_SOFT_FILL` | 0.25 | start paced `sync_file_range` flushing |
| `WAL_CKPT_CYCLE_FILL` | 0.50 | back-to-back full cycles |
| `WAL_STALL_FILL` | 0.90 | writers wait for checkpoint progress |
| `WAL_STALL_TIMEOUT_MS` | 5000 | max stall before the batch fails "overloaded" |
| `WAL_CKPT_MAX_AGE_MS` | 5000 | oldest unsynced dirty range that forces a cycle (env `XSTORE_CKPT_MAX_AGE_MS`) |
| `WAL_CKPT_IDLE_MS` | 50 | writer idle time that triggers a cycle (env `XSTORE_CKPT_IDLE_MS`) |
| `WAL_FLUSH_CHUNK_BYTES` | 4 MiB | paced flush granularity |

`XSTORE_WAL_STATS` builds additionally log total `ring_records`, `direct_records` and `ring_stalls` with the per-shard batch statistics.

**Measured behaviour.** One noisy box (load1 0.8–4.4 during the gates, other processes running), interleaved A/B, so **indicative, not authoritative**. The baseline is the pre-ring binary built from `a28af4cd`; it fdatasyncs the WAL but gives **no durability past an OS crash**, so it is a speed reference, not an equivalent. Scripts and raw logs: `.superpowers/sdd/2026-10-02-wal-ring-checkpoint/` (`gate9.sh`, `bulk_probe.py`, `restart_probe9.py`, `*.log`).

- **End-to-end SYNC through the real server** (bulk inserts over ZMQ, the meaningful measurement): small records ≈ 0 %. Medium records (batch 1000, 136 KB, ring path): −9 % on a 700k-row, ~9 s run, but **+10 %** on a 2.5M-row, ~40 s run (63.2k → 69.5k rows/s) — the short run flatters the baseline, whose disk flush is simply deferred past the measurement window. Large records on the direct path (batch 20000, 2.7 MB): **+6.6 %** at 700k rows (124.9k → 133.1k rows/s) and ≈ **+10 %** on a 4M-row (545 MB) sustained run (two rounds each, request p99 similar); the cause was not isolated (the direct path skips the WAL write, which is the likely difference). RSS equal for small loads (~68 MB), **≈ +35 MB on the bulk runs** (405–422 vs 369–389 MB).
- **In-process perf tests** (`xstore_perf_tests`, ASYNC default) measure enqueue throughput and cannot resolve differences below ~10 %: Batch/Range 200k and 1M rows ranged −1.8 % to −10.2 %, Concurrent8 +17 % in one gate and −7.8 % in the next, UnarySync +0.5 %. Treat these as noise. Unary ASYNC (100k, five rounds, medians) is **−0.5 %** (44,104 vs 43,864 inserts/s) with the production ring.
- **Which perf tests mean what.** `BatchInsertThroughput` / `RangeInsertThroughput` use the proto default (ASYNC) and so time **enqueue only**. The meaningful durable-write numbers are the SYNC variants, `BatchInsertThroughput_Sync` and `RangeInsertThroughput_Sync` (reported as `BatchInsert[SYNC]` / `RangeInsert[SYNC]`: the call returns once every row is WAL-durable and applied), and `UnaryInsertThroughput_Sync`. `BatchQueryThroughput` / `RangeQueryThroughput` insert with SYNC so the query phase sees the rows. Perf runs must set `XSTORE_TEST_RING_BYTES=67108864` (the production ring); the 8 MiB test default makes the checkpointer run constantly and skews every insert number.
- **Methodology lesson.** The first gate reported −7.4 % on Unary ASYNC. That was an artifact: the perf binaries inherited the 8 MiB *test* ring, and ~22 MB of log into an 8 MiB ring kept hitting the 50 % fill trigger, so the checkpointer ran about 2000 cycles in a 5 s run (strace). A perf profile showed `Dirty().Note` at 0.07 % and ring code at ~1.7 %. Perf runs must set `XSTORE_TEST_RING_BYTES=67108864`.
- **Shutdown and restart** (700k SYNC rows, one year): SIGTERM stop **1.43 s → 0.28 s** (the final cycle syncs only dirtied ranges; the old shutdown synced every cached fd); restart after SIGTERM 0.15 s in both. **SIGKILL restart to first MIN query is unchanged, ~62–66 s** (61.9 s baseline, 65.8 s ring): dirty flags and replayed years force a full-year index rebuild, which dominates; incremental recovery is phase 2 (`TODO.md`).

**Crash-test methodology and limits** (`WalCrashSimTest` and neighbours, `tests/integration/XStoreWalRingTest.cpp`). The model is *page-cache loss*: after every checkpoint cycle and after every acknowledged direct write the test copies each tracked data file as its **durable image** (what an `fdatasync` guarantees); a simulated power loss is `WalSimulateRestartForTests()` + restoring those images over the data files, keeping the ring files, + `InitDB`, after which every acknowledged row must be readable with `UnaryQuery`. Scenarios: acknowledged SYNC rows with a large and a tiny ring, a large direct batch, repeated overwrites of one timestamp (newest wins, small ring record then large direct record), a crash storm, concurrent writers against the checkpointer, a poisoned checkpointer followed by power loss, and the every-insert-API-notes-its-file audit. **What this proves:** the invariant holds under any interleaving the scheduler produced — no row is acknowledged whose bytes are in neither the ring nor a synced data file — and that replay restores them. **What it cannot prove:** torn writes within a page or sector; out-of-order sector persistence; directory-entry durability; that `fdatasync` does what it promises (the model trusts it, each snapshot moment is paired with a sync-counter assertion in only two tests); index content after recovery (only `UnaryQuery` is verified, not aggregates, pattern search or rebuilt `.zmap`/`.catidx` content). *Mutation checks* (each turned the matching test red in a scratch tree): removing the ring-clear rule; skipping the cycle's data `fdatasync`; ignoring poison; removing `Dirty().Note`; skipping the direct path's `fdatasync`. *ThreadSanitizer* (scratch build, jemalloc off): 80 tests (`WalCheckpoint*`, `WalDirectPath*`, `WalCrashSim*`, `WalRingWriter*`, `WalReplay*`) clean, no lock-order inversions; the first run's 16 reports were all a **test teardown bug** (an ASYNC poll returned while the writer was still updating the zone map and catidx, and `TearDown` destroyed objects underneath it), fixed by waiting for the ring's applied position to reach head. The older ASYNC tests have not been audited for the same hazard. Several recovery paths are covered by reasoning-based RED only (the production code was written before the tests): the `CommitReplay`-failure fence, the no-matching-ring fence, and a crash between the two zeroing syncs have no direct test.

**Known limits and accepted residual risks.**
- *Torn tail, out-of-order persistence.* A torn record that leaves an all-zero hole in front of an intact next record (sectors persisted out of order) is not zeroed by replay, and a torn record whose first sector (the one holding the LSN field) was lost reads as a clean end. In those rare cases an **unacknowledged** write can reappear after a later crash, and can overwrite an *acknowledged* value only if both writes used the same timestamp. A possible fix is a scan-ahead for CRC-valid records whose LSN equals their position's expected LSN (`TODO.md`).
- *Mid-log corruption.* Replay stops at the first bad record and moves the checkpoint there, so valid records after a corrupt middle record are discarded (as with the legacy format).
- *Failed WAL sync.* A failed WAL write/`fdatasync` leaves possibly CRC-valid bytes ahead of head; they are zeroed best-effort. If that zeroing (or its `fdatasync`) also fails, a crash can replay a record whose caller was told it failed (at-least-once ambiguity). Likewise a crash after a failed ring sync may replay a write the caller saw fail.
- *Cross-shard replay order.* Rings are replayed one shard at a time in shard-index order, so two un-checkpointed writes to the **same row** on different shards can replay in a different order than they were acknowledged. This is a pre-existing property of the multi-shard design (the old WAL had it). In practice it is limited here: `EnqueueWalRecord` salts a DB across `WAL_SHARDS_PER_DB` shards with `std::hash<std::thread::id>` of the calling thread, and observed on this box/glibc that hash does not spread threads (64 threads landed on one shard), so one DB ≈ one shard and the salting is effectively inert. It also means the benchmarked `WAL_SHARDS_PER_DB` = 4 "regression fix" (`TODO.md`) may not behave as written.
- *Not WAL-covered.* BYPASS inserts (their rows are noted dirty and so synced by a later cycle, but nothing is promised) and hole-punch deletes (not logged, so a crash can resurrect a deleted row; since the durability fix round each successful punch is *noted dirty*, so the next cycle and the final cycle of a clean stop `fdatasync` it). ASYNC acknowledges before the WAL sync, and an ASYNC record in a sub-batch that times out or fails is dropped after the caller was told success. A record whose rows fail to apply for a live DB in the *writer* path is reported failed to its caller, but the ring is already durable, `applied_lsn` still advances and the checkpoint may pass it (pre-existing semantics; the *replay* path fences instead).
- *In flight at a signal.* A SYNC insert in flight at SIGTERM/SIGINT may be durable but unacknowledged (§4.18).
- *Directory entries.* Only the immediate parent directory of a data or ring file is fsynced; the entry of `DataStore/<DB>` and of `DataStore/WAL` inside `DataStore` is not (pre-existing).
- *Syncs use a throwaway fd.* Data-file syncs open the file by path. By the Linux errseq model a writeback error already reported to another descriptor (for instance by the startup index rebuild's `fdatasync`) would not be reported to the new one; the checkpointer has no other fsync caller on data files at runtime, so this is believed theoretical.
- *`GetOrMapFile`* maps data files `PROT_READ, MAP_SHARED` (all callers only read; every write is a `pwrite()` the dirty tracker sees). A store through the mapping faults instead of silently bypassing the tracker; `MAP_SHARED` keeps concurrent `pwrite()`s visible through it.
- *`AnyFenced()` is process-wide.* One fenced shard disables the direct path for every DB until a later replay of that file succeeds or the process restarts. A legacy WAL whose data sync fails stays legacy, and its shard's inserts fail until restart.
- *Rollback hazard.* A binary from before the ring format treats a ring file as an empty/invalid WAL and overwrites it, discarding the un-checkpointed acknowledged writes in it. Roll back only after a **clean SIGTERM** stop (whose final cycle checkpoints every ring); never after a crash or SIGKILL.
- *First start / legacy upgrade cost.* Creating (or converting) a ring zero-fills and `fsync`s 64 MiB per shard (`WAL_RING_BYTES`) with the ring registry mutex held, so the first start, or the first insert to a fresh data directory, can take about a second per shard before the first record is accepted.
- *`RemoveDB` / `RemoveDBFiles` checkpoint first.* Before unlinking, a synchronous checkpoint cycle runs so every acknowledged record for the doomed DB is behind the checkpoint (otherwise a DB re-created under the same name with a different row length would be corrupted by replay, and removed years would reappear). A failed or refused cycle (poisoned checkpointer) is logged as a WARNING and the removal proceeds. ASYNC records still queued, not yet applied, at that moment are not covered.
- *Hole-punch deletes are noted dirty,* so a clean stop syncs them (see *Not WAL-covered* for what is still not promised).
- *Boot hold.* The checkpointer's idle trigger is held off for the duration of `ReplayWal` (a counter taken by an RAII guard): replay notes files while no writer has run yet, which would otherwise read as "dirty and idle for decades" and cycle every millisecond against the replay's own syncs. The fill, max-age and retry triggers keep working.
- *Large records.* A multi-row record larger than half the ring on a file with un-checkpointed ring records waits for checkpoint cycles and then fails as "overloaded" (log only; clients see the generic failure). The 5 s bound is checked only *between* cycles: one long in-flight cycle holding the cycle mutex can push the wait past 5 s; a single-row record larger than half the ring always fails.
- *Slow SIGKILL test.* `XStoreGracefulShutdownTest.SigkillLeavesIndexesDirty...` takes ~55 s: `CreateDB` accepts only SECOND/MILLI/MICRO resolution, so replay re-extends the year file to ≥ 31.5M rows and forces a full index rebuild; it sets both `XSTORE_CKPT_*` knobs huge so the kill always lands with a record un-checkpointed.

## 5. Concurrency Control

### 5.1 In-process byte-range locking — `FileRangeLock` / `FileLockRegistry`

Replaces POSIX `fcntl()` record locks, which are scoped to the **process** (not thread or fd) and therefore provide **no** mutual exclusion between XStore's worker threads (each of which independently opens/maps the same files) — `fcntl()` locks would have been silently ineffective for this concurrency model.

```cpp
class FileRangeLock {                  // one instance per file path
  bool Conflicts(start, end, type) const;   // overlap AND (either side WRITE)
  void LockRange(start, length, type);      // blocks (condvar) until no conflict, then registers
  void UnlockRange(start, length, type);    // O(1) swap-and-pop removal, notify_all()
  std::vector<ActiveLock> ActiveLocks;      // linear scan — bounded by worker thread count
};
class FileLockRegistry {               // process-wide, sharded: 16x {shared_mutex, path->FileRangeLock map}
  static FileRangeLock& Get(path);     // hash(path) % 16 picks the shard; shared lock on hit, exclusive+double-check on first-touch miss
};
class FileRangeLockGuard { /* RAII: guarantees UnlockRange runs even on exception/early return */ };
```

- **Semantics:** two ranges conflict only if they **overlap** *and* **at least one side is WRITE**. Disjoint ranges of the same file never block each other regardless of type — unrelated rows/years can be written concurrently by different worker threads. Both-READ overlapping ranges are compatible (shared).
- **`length == 0`** is a sentinel for "rest of file" (kept for compatibility with the old `fcntl` convention) and conflicts with every other range.
- **Conflict check is a linear scan** over `ActiveLocks` (a flat `std::vector`, not a node-based container) — deliberately, since concurrently-held ranges per file are bounded by the worker thread count, making a flat vector cheaper (no per-lock heap allocation, better cache locality) than a tree/map.
- **RAII guard is a correctness fix, not just convenience:** a missed unlock under the old `fcntl` code was a harmless no-op (released automatically on `fclose()`); under this in-process model a missed unlock is a **permanent hang** for any other thread waiting on that range, hence the guard guarantees `UnlockRange` runs on every exit path including exceptions.
- **Registry sharded 16-ways (commit `d6b9ffe`):** `FileLockRegistry::Get()` is called on *every* op (Unary/Batch/Range Insert/Query/Delete, every call, not just on lock contention), so a single global `shared_mutex` guarding the whole `path → FileRangeLock` map was a serialization point shared by all files, not just contending writers of the same file — threads touching completely unrelated files/DBs still bounced the same mutex's cache line. Sharded by `hash(filePath) % 16` (same pattern as `CfgShards`/`FdShards`/`MmapShards`), unrelated files' lookups now usually land in different shards and share no lock at all; only a first-touch on a still-unregistered path (or a same-shard hash collision) briefly takes that shard's exclusive lock.

**Locking granularity trade-off (explicitly noted as tried at both extremes):** per-row locking and whole-span locking were both implemented and benchmarked; whole-span (one lock covering a batch/range group's full min-to-max offset) won and is what `WriteRowGroupToFile`, `RangeQuery`, `WalkYearSpan`, and `BatchDelete` all use. The write *coalescing* (fewer `pwrite`/`pread` calls) is a separate, independently-tunable axis from the *lock* granularity — a whole-span lock does not require a whole-span write; `WriteRowGroupToFile` derives its run-splitting from actual offset contiguity, not from the lock span.

### 5.2 Threading model

One OS thread per configured worker (`ZMQ_Server::NumThreads`, set from a CLI argument), each running an infinite `recv → process → send` loop (`WorkerRoutine`) and owning:
- **Its own `XStore` instance** — stateless per-call logic; the constructor is idempotent per distinct `DataStoreDir` (guarded by a `static` mutex + `unordered_set<string>` of already-initialized dirs), so directory creation + config-cache warm-up (`InitDB()`, a full scan of existing DBs) happens once per process, not once per thread, even though many `XStore` instances are constructed (this also lets tests construct many `XStore` instances against many distinct scratch directories within one process without re-triggering the scan).
- **Its own `google::protobuf::Arena`**, reused via `Arena.Reset()` every iteration rather than reconstructed — keeps the arena's already-allocated blocks around for the next request instead of returning them to the system allocator, so steady-state traffic pays only bump-pointer allocation cost, not block-list malloc/free churn (§7.2).
- **Its own reusable `std::vector<zmq::message_t>`** receive buffer (`.clear()`, not reconstructed, each iteration).

Other long-lived threads: one WAL writer per active shard (`WalWriterLoop`, §4.12) and the single WAL checkpointer (§4.19), both started by `StartWalWriters`; at shutdown the writers are joined first, then the checkpointer runs its final cycle and is joined (`StopWalWriters`, §4.18/§4.19).

Signals: `main` blocks SIGINT/SIGTERM before any thread starts and one dedicated thread `sigwait`s on them to trigger the graceful stop (§4.18); the worker threads never see these signals.

The `XStore` class's **shared state** (mmap/fd/config caches, `FileLockRegistry`) is `static` and therefore genuinely process-wide/cross-thread — this is intentional: the caches and locks must be shared across worker threads, since concurrent workers may touch the same file, while the request-processing logic (`XStore`'s non-static members are all path/config helpers with no per-call mutable state beyond what's passed in) is safely duplicated per thread to avoid any need for per-request synchronization on the "business logic" itself.

## 6. Query & Aggregate Execution

### 6.1 `WalkYearSpan` — shared scan driver

```cpp
template <typename Kernel>
void XStore::WalkYearSpan(dbBasePath, cfgStruct, startEpochT, endEpochT, Kernel &&kernel);
```

Common to `MinAggregate`/`MaxAggregate`/`SumAggregate`/`AvgAggregate` (and `RangeQuery`/`RangeDelete` follow the same *shape*, though they aren't literally routed through this template): walks `[start, end]` one year-file at a time, and for each existing year:
1. `GetOrMapFile` — cached mmap (§4.5).
2. Take one READ `FileRangeLockGuard` over that year-segment's byte span.
3. `madvise(MADV_WILLNEED)` over the (page-aligned) span — a **bulk prefetch hint** issued once per segment instead of relying on lazy per-page faulting as the kernel scans forward. This matters more for aggregates than for `RangeQuery` because aggregate kernels always walk the **full span with no early exit** (every row must be visited to compute min/max/sum), so the entire region is guaranteed to be touched.
4. Invoke `kernel(rowsBase, rowsToProcess)` — a pointer directly into the cached mapping, no per-call `mmap()`/`munmap()`.

A missing year contributes nothing (the kernel simply isn't called for it) — consistent with how `RangeQuery`/`RangeDelete` treat a missing year (zero entries / zero deletes), as opposed to a *hole within an existing year*, which is a real (zeroed) row that participates as "no valid data for this timestamp" rather than being silently skipped from iteration.

Since commit `8c6c4fc`, `WalkYearSpan` is invoked two ways: directly (narrow spans, and internally by `WalkYearSpanParallel` below for the sequential fallback), or once per segment from inside a parallel worker thread (wide spans) — see §6.4. The per-call logic (steps 1–4 above) is identical either way; only *how many times* and *from which thread* it's invoked changes.

### 6.2 Skip-parse column extraction — `ExtractColumnByIndexSkipParse`

The aggregate kernels only ever need **one column** (`columnIdx`) out of a row. The original implementation fully parsed every row into a `RowData` (`MergePartialFromCodedStream`), decoding and heap-allocating an `FData` for every column, then discarded all but one. `ExtractColumnByIndexSkipParse` instead walks the row's raw protobuf wire bytes directly:

```cpp
while ((Tag = CodedIn.ReadTag()) != 0) {
    if (WireFormatLite::GetTagFieldNumber(Tag) != RowData::kFieldDataFieldNumber) {
        if (!WireFormatLite::SkipField(&CodedIn, Tag)) return false;
        continue;
    }
    if (Occurrence == columnIdx) return WireFormatLite::ReadMessage(&CodedIn, &outData);
    if (!WireFormatLite::SkipField(&CodedIn, Tag)) return false;
    ++Occurrence;
}
return false;  // ran out of columns before reaching columnIdx
```

Every non-target column is skipped by **cursor advance only** (`WireFormatLite::SkipField`) — no `FData` object is constructed for it. `ReadTag() == 0` is the same end-of-row/short-row signal the old full-parse path relied on via `fielddata_size()` bound checking. One deliberate semantic difference from full-row parsing: because this returns as soon as the target column is read, corruption in a *later* column no longer fails the read of an earlier, valid target column the way a full-row parse would (a relaxation, not a regression, for this use case).

**Measured impact:** benchmarked ~40–54% faster than the old full-parse kernel across N = 100/1k/10k rows (commit `764999e`; the A/B perf-test harness that produced this number was removed after the skip-parse kernel was promoted to the only implementation, since there was no longer a second kernel to compare against).

### 6.3 Aggregate kernels

```cpp
template <typename Cmp>
void ProcessFileRangeSelect(rowsBase, totalRows, rowLen, columnIdx, ValueStruct& best, FData& bestData);
//   Cmp = std::less<long double>    -> MIN
//   Cmp = std::greater<long double> -> MAX

void ProcessFileRangeAccumulate(rowsBase, totalRows, rowLen, columnIdx, double& sum, uint64& validCount);
//   backs SUM directly; AVG = sum / validCount after the same accumulate pass
```

Both kernels: for each row, skip if the first byte is `0` (hole, §3.2); else `ExtractColumnByIndexSkipParse`; if the extracted `FData`'s `oneOfData_case()` is one of the 12 **numeric** variants (string/bytes/bool are excluded — the `case() > 0 && case() <= 12` check), coerce it to a scalar via `GetFDataValue`'s type-switch and fold it into the running best/sum. `ProcessFileRangeSelect` is **explicitly instantiated** for exactly the two comparators ever used (`std::less`/`std::greater<long double>`), so the compiler generates two fully-inlined, branch-free (on `Cmp`) versions with no `std::function`/vtable indirection.

`ValueStruct` is a minimal `{unsigned int Index; long double Value; bool IsInitialized;}` — `long double` is used as the common comparison type across all 12 numeric protobuf wire types so `ProcessFileRangeSelect` doesn't need a template per source type.

### 6.4 Multi-year parallel aggregate scanning — `WalkYearSpanParallel`

```cpp
template <typename PartialState, typename SegmentKernel, typename MergeFn>
PartialState XStore::WalkYearSpanParallel(dbBasePath, cfgStruct, startEpochT, endEpochT,
                                            PartialState initialState, SegmentKernel &&segmentKernel, MergeFn &&mergeFn);
```

Added in commit `8c6c4fc`. All four aggregates (`Min`/`Max`/`Sum`/`AvgAggregate`) now route through this instead of calling `WalkYearSpan` directly:

1. **Enumerate segments first** — one `[Start, End]` pair per calendar year in `[startEpochT, endEpochT]`, computed via `TimeStruct` the same way `WalkYearSpan`'s internal loop does. This is O(#years), not O(#rows), so it's cheap even for a wide span, and lets the function decide up front whether parallel dispatch is worth it before committing to any thread spawning.
2. **Narrow span (`< kMinSegmentsForParallelWalk` = 4 distinct years):** delegates straight to a single `WalkYearSpan` call over the whole `[startEpochT, endEpochT]` — byte-identical code path to before parallelism existed, no threads, no merge step. This is the common case: perf-suite defaults and most real queries never span more than a handful of years, and thread creation (tens of microseconds each) plus the final merge isn't worth paying for a span the sequential walk finishes just as fast anyway.
3. **Wide span (≥ 4 years):** spawns `min(#segments, hardware_concurrency())` `std::thread`s, **striped** across segments (thread *t* takes segments *t, t+NumThreads, t+2·NumThreads, …*, not a contiguous chunk) so a handful of unusually large years don't all land on one thread. Each thread accumulates into its **own** `PartialState` (never a value shared across threads — protobuf/`ValueStruct` objects aren't safe for concurrent mutation even on logically-disjoint fields per protobuf's own thread-safety docs), calling `WalkYearSpan` once per segment it owns (each segment falls entirely within one year, so `WalkYearSpan`'s internal loop runs exactly once per call — same `GetOrMapFile`/lock/`madvise`/kernel logic as the sequential path, just invoked per-segment).
4. After `join()`, `mergeFn(finalState, partialState)` folds each thread's partial result into the running total **sequentially** — O(#threads), not O(#rows).

`MinAggregate`/`MaxAggregate` use a `MinMaxPartial{ValueStruct Value; FData Data;}` partial state, merging by strict improvement only (never on a tie — same rule `ProcessFileRangeSelect` itself uses); ties **across** different threads' segments resolve by thread/segment processing order rather than strict chronological order in that specific case, a relaxation not exercised by any current test and considered acceptable since real sensor/metric data essentially never produces an exact cross-year tie on an extremum. `SumAggregate`/`AvgAggregate` use a `SumPartial{double Sum; uint64 Count;}`, merged by plain addition — narrow spans are untouched (byte-identical to the pre-parallel sequential sum, including the exact-value check in `SumAggregateMatchesIndependentlyComputedSumFromRawDiskBytes`), but a wide-span parallel sum **reassociates** the floating-point addition relative to a strict single-pass left-to-right sum (per-year partial sums combine in a different order), which can differ by a few ULP from the sequential result for the same data — an inherent property of any correct year-parallel sum, not an avoidable implementation choice.

**Cross-request thread-pool scope (verified, corrected):** `WalkYearSpanParallel`'s `hardware_concurrency()` cap bounds only *this request's own* thread count — it has no visibility into other concurrent requests' thread spawns. There is a real, if incidental, partial bound worth crediting: each aggregate request runs synchronously on one ZMQ worker thread for its entire duration (a `REP` socket enforces strict recv-then-send ordering), so the number of *concurrently in-flight aggregate requests* is capped at the ZMQ worker count (physical core count by default). But that cap doesn't bound *threads spawned per request* — each in-flight request can still independently spawn up to `hardware_concurrency()` more threads, so the two caps multiply rather than nest (`workers × hardware_concurrency()`; worst case several hundred threads on a modest multi-core box). This has not been exercised by any perf or integration test at the concurrency level that would expose it — the in-repo perf suite's aggregate benchmarks are single-year (never reach the parallel path at all), and the "benchmarked under 4-concurrent wide-span load, no clear regression" data point referenced in earlier revisions of this document was an ad hoc manual run, not a checked-in regression test. A pool-based fix already exists elsewhere in this codebase and could be applied here: `XStorePreadPool::ParallelFor` (§6.2's sibling infrastructure, used by `BatchQuery`) already caps total concurrent work items pool-wide via a ticket model — routing `WalkYearSpanParallel`'s segment work through it instead of raw `std::thread` spawn would give this exactly the cross-request coordination it currently lacks. Tracked in `TODO.md`.

**Measured impact:** 5.08x speedup on wide multi-year aggregate queries; no measurable regression on narrow/single-year throughput.

**Removed in the same commit:** the previous §6.4, `ProcessFileRangeSelectTypedDouble`/`MinAggregateTypedDouble` — a profiling-only MIN kernel that skipped `ExtractColumnByIndexSkipParse` for a full `RowData` parse and compared `doubleData` natively (no `GetFDataValue` switch, no `long double` promotion), used only to measure the delta a fully type-specialized kernel would buy over the generic skip-parse path. Deleted along with its perf-suite A/B tests once that comparison had served its purpose — it was never part of the four-aggregate production API surface.

## 7. Networking Layer

### 7.1 ZeroMQ broker topology

```cpp
zmq::socket_t ClientSocket(Ctx, zmq::socket_type::router);  // faces clients, tcp://<addr>:<port>
zmq::socket_t WorkerSocket(Ctx, zmq::socket_type::dealer);  // faces workers, inproc://workers
zmq::proxy(ClientSocket, WorkerSocket, nullptr);            // broker: load-balances client reqs across workers
```

Each of `NumThreads` worker threads connects a `REP` socket to `inproc://workers` and runs an independent `recv → dispatch → send` loop. This is the classic ZeroMQ **ROUTER-DEALER broker / REP worker pool** pattern: the broker transparently multiplexes many concurrent client `REQ` connections onto a fixed worker pool, and `zmq::proxy` handles the envelope routing so individual workers never see client identity framing directly — they just `recv`/`send` one request/response per REP-socket round trip.

**Graceful stop (2026-10, §4.18):** `ZmqServer::RequestStop()` calls `zmq_ctx_shutdown`; the proxy and every worker's blocking `recv`/`send` then fail with `ETERM` and the workers exit. `StartServer` returns `bool`: true once all (detached) workers have left, within a 10 s bound (`ZMQ_SHUTDOWN_DRAIN_TIMEOUT_S`); false on timeout, in which case `main` exits 1 without running `XStore::Shutdown()`.

### 7.2 Per-request allocation strategy — Arena

```cpp
google::protobuf::Arena Arena;      // one per worker thread, constructed once
...
while (true) {
    Arena.Reset();                  // frees everything from the previous request in one shot
    auto *Req = google::protobuf::Arena::Create<Request>(&Arena);
    Req->ParseFromArray(...);
    ...
    auto *Rep = google::protobuf::Arena::Create<BatchQuery_REP>(&Arena);  // for wide/nested response types
    MyStore.BatchQuery(Req, Rep);
    SendProto(Socket, *Rep);
}
```

Applied selectively: **incoming requests whose payload nests repeated messages** (`BatchInsert_REQ`, `RangeInsert_REQ` — each row is a `RowData` → `repeated FData`) are parsed straight into arena memory automatically as part of parsing the top-level `Request`, no extra code needed at the call site. **Response types with nested repeated fields** (`UnaryQuery_REP`, `BatchQuery_REP`, `RangeQuery_REP` — each response row owns its own `RowData` → `repeated FData`) are explicitly `Arena::Create`'d, since under the ordinary allocator a wide/long response means one heap allocation per row plus one per column inside it. Response types that are just a flat status string (`CreateDB_REP`, `RemoveDB_REP`, `UnaryInsert_REP`, `BatchInsert_REP`, `RangeInsert_REP`, delete-family `_REP`s) are **not** arena-allocated — there's nothing nested to save an allocation on, so a plain stack-local suffices.

`UnaryQuery` is called out in-code as likely the **highest-QPS RPC** (single-row point queries, not scaled by span like `RangeQuery`) — its response is arena-allocated even though it's not "wide," because the per-call cost (one allocation, paid on *every* call with zero reuse across calls) matters even at a small constant size once QPS is high enough.

### 7.3 Request dispatch

`Request::payload_case()` (the `oneof` tag) is the single dispatch key — a `switch` over 18 cases (17 RPC kinds + `PAYLOAD_NOT_SET`) in `WorkerRoutine`. An unrecognized/empty payload still gets an (empty) reply sent, so a client's `REQ` socket (which enforces strict send-then-recv ordering) is never left hanging on a request the server silently drops.

### 7.4 Response serialization

Most RPCs — everything except `BatchQuery`/`RangeQuery` — reply via a single-frame helper:

```cpp
template <typename T> void SendProto(zmq::socket_t &socket, const T &msg) {
    size_t Size = msg.ByteSizeLong();
    zmq::message_t Reply(Size);
    msg.SerializeWithCachedSizesToArray(Reply.data());  // reuses ByteSizeLong()'s result, not a second size pass
    socket.send(Reply, zmq::send_flags::dontwait);
}
```

`dontwait` is kept for parity with the original fire-and-forget send (no result check) — on a `REP` socket, ZeroMQ's own recv-then-send state-machine enforcement means the send can't actually block here regardless of the flag.

**`BatchQuery`/`RangeQuery`: streamed, skip-copy multipart replies.** These two RPCs never build a full response object tree. `include/XStore/XStore_WireEncode.h` walks each row's on-disk bytes with a `CodedInputStream`/`WireFormatLite` cursor (`RealRowDataLength()`) to find the row's true serialized length (skipping the zero-padding), then hand-writes the wire tags for one `UnaryQuery_REP`-shaped entry (`queryresponse` field, inner `timestamp`+`data`) directly into an outbound chunk buffer — copying the on-disk row bytes verbatim rather than constructing a `RowData`/`FData` object graph and re-serializing it. Chunks are capped at `XStoreTunables::STREAMED_QUERY_CHUNK_SIZE_BYTES` (64MB) and sent as successive ZMQ frames (`sndmore` on all but the last); the client's `SendRecv` reassembles all frames into one buffer before a single `ParseFromArray` call (protobuf doesn't care where the bytes were split, only that they're concatenated in order).

- **Pros:** server-side peak memory for a query never exceeds one chunk, regardless of how large the eligible result is — this is what let a prior full-object-tree-per-response design's permanent RSS floor under Arena `Reset()` (see §9) go away entirely for these two RPCs.
- **Cons:** this only bounds server memory. It does not lift protobuf's ~2GB message ceiling, since the client still reassembles everything into one buffer before parsing — a request whose *total* result would exceed 2GB is rejected up front, before any chunk is built (§11).
- **What's novel:** skip-copying raw, already-serialized row bytes straight into the outbound wire format — reusing the same wire-tag-walk technique the aggregate kernels use for skip-parse (§6.2), just applied to encoding instead of decoding — avoids the allocate-decode-then-reallocate-reencode round trip a naive streaming implementation would still pay per row.

### 7.5 Optional transport encryption/auth — ZMQ CURVE

Both sockets above — the RPC ROUTER socket (§7.1) and the SysStats PUB socket — default to ZMTP's `NULL` mechanism: no encryption, no authentication, unchanged from before this feature existed. Passing `--curve` at boot (plus `--curve-secret-key`/`--curve-allowed-dir`, both defaulted per `xstore-keys`' directory convention when omitted) switches both sockets to libzmq's built-in CURVE mechanism (Curve25519, backed by `libsodium`):

- **Key management:** `FilesystemKeyStore` (`include/Networking/XStore_Curve.h`) is a directory-backed allowlist — one Z85-encoded `.pub` file per authorized client identity under `--curve-allowed-dir`. It re-scans on a debounced `stat()` check (`CURVE_ALLOWLIST_MIN_CHECK_INTERVAL_MS`, default 1000ms), so revoking a client takes effect on its *next* connection attempt with no server restart required. The `xstore-keys` CLI (`tools/xstore-keys/`) generates keypairs and manages the allowlist directory directly on disk (`gen`/`allow`/`revoke`/`list`) — it talks only to the filesystem, never to a running server.
- **Authentication:** one `XStoreZapHandler` (an RFC 27 ZAP responder thread, bound to `inproc://zeromq.zap.01` on a given `zmq::context_t`) answers each incoming handshake by checking the connecting peer's public key against the shared `FilesystemKeyStore`. `ZmqServer::StartServer`'s ROUTER socket and `SysStatsCollector::Start`'s PUB socket each run their own handler on their own context (the two already ran on separate contexts before this feature), sharing one server keypair and one allowlist.
- **Scope:** CURVE is applied only to the external-facing sockets. The ROUTER's `inproc://` DEALER/REP legs behind it (§7.1) have no ZMTP handshake and no wire-security concept, so enabling CURVE there would be a no-op at best.
- **Opt-in guarantee:** omitting `--curve` server-side, or the equivalent client-side curve parameters (`XStoreClient`'s optional `curve_auth`, `XStore.py`'s `curve_*_file` kwargs), leaves every socket on `NULL` — byte-for-byte unchanged from pre-CURVE behavior.

Full rationale, threat model, and the explicitly-deferred items (a universal CLI config file, mid-session forced disconnect on revocation, a real etcd-backed `KeyStore`) are in `docs/superpowers/specs/2026-09-09-zmq-curve-auth-design.md`.

## 8. Client Libraries

### 8.1 C++ (`client_src/Cpp/XStore_Client.h`) — header-only

- All 17 RPCs funnel through one templated `SendRecv<RepT>(const Request&)`: serialize → blocking `send` → blocking `recv` (`zmq::recv_multipart` into a reused member buffer) → parse. Centralizing this means the 17 call sites can't drift out of sync the way hand-copied send/recv blocks would.
- **Timeout semantics:** constructor takes `timeoutMs` (default −1 = block forever, matching legacy behavior). A `REQ` socket that hits a send/recv timeout is left in an **undefined state machine position** per ZeroMQ's own documentation — the documented fix is a fresh socket, not a retried send, hence `Reconnect()` exists as an explicit required step after catching a timeout, rather than being automatic/hidden.
- **Warmup:** `Ping()` (RPC #18, added specifically for this — an empty round trip with no server-side `XStore` work) forces the lazy `connect()`'s TCP + ZMTP handshake at construction time (`warmupOnInit`, default `true`) rather than on the first real RPC, so the first *business* call doesn't eat handshake latency. `InfoRequest()` was previously (ab)used for this and does strictly more server-side work (directory scan) than necessary for a pure liveness/warmup check.
- Batch/Range insert helpers offer both a convenience overload (`vector<pair<timestamp, RowData>>`, internally Arena-built to amortize per-row submessage allocation for large batches) and an advanced overload that accepts a pre-built request message directly (move-friendly, for callers who want to reuse/construct the message themselves).
- `XStore_FData::Double()/Int32()/String()/...` factory helpers exist because proto3 gives `sint32`/`fixed32`/`sfixed32` (etc.) the *same* C++ parameter type (`int32_t`) despite different wire encodings — overloading on parameter type alone can't disambiguate them, so intent is named explicitly instead.
- **`SuggestRowLength<Alignment=8>`** — a static helper that estimates a `rowLength` to pass to `CreateDB`, given one sample `RowData`: switches on each `FData::oneOfData_case()` (including the `NOT_SET`/hole case, handled as zero-cost), sums `sizeof(type) + PROTOBUF_FIELD_OVERHEAD` per field, rounds up to `Alignment`. This is a **pre-`CreateDB` sizing estimate** from a hypothetical sample row — a forward-looking convenience, not an audit of an already-configured DB's real usage (that's a separate, already-solved problem — see the `xstore-viewer` tooling below).

### 8.2 Python (`client_src/Python/XStore.py` + generated `XStore_pb2.py`)

Generated from the same `XStore.proto` (kept in sync with the C++ server's `Request`-envelope/oneof protocol — commit `115db5e` specifically fixed the Python client to wrap requests in the `Request` envelope and resync its generated `_pb2.py` after the server-side protocol changed, which is a concrete example of the wire-schema/client drift risk inherent to hand-maintained multi-language clients against one `.proto`). Kept in feature parity with the C++ client, including `WalDurabilityMode` exposure and a Python equivalent of `SuggestRowLength`.

### 8.3 Tooling — `xstore-viewer`

A separate desktop/web-server tool (`tools/xstore-viewer/`, Rust backend + JS frontend) for browsing DBs, running ad hoc queries, and surfacing operational diagnostics that don't belong in the wire protocol itself. Notably, it implements the **row-size sizing guide** — sampling real query results, computing each row's true serialized size (`convert.rs`, via `encoded_len()`), and comparing that against the DB's configured `rowLength` (from `DbStats`) to flag wasted padding or truncation risk (`app.js`'s `slotBadge()`, rendered in the DB list and status bar as "too small" / "N% waste" / OK). This is the functional answer to "is `rowLength` sized well for this DB" — a diagnostic that lives in the viewer rather than the client library, since it needs a live query result to sample against, not just a hypothetical row.

## 9. Optimization History (Design Evolution)

The git history is a sequence of individually-justified, often individually-*measured* performance changes. In rough chronological/causal order (not strictly commit order):

| Change | From → To | Motivation |
|---|---|---|
| Locking primitive | `fcntl()` process-scoped record locks → in-process `FileRangeLock`/`FileLockRegistry` byte-range locks | `fcntl()` locks don't provide mutual exclusion *between threads* of the same process — ineffective for a thread-pool concurrency model. |
| Insert I/O path | `PROT_WRITE` mmap + memcpy → cached fd + `pwrite()` | mmap write-faults into untouched pages synchronously allocate a block before returning; `pwrite()` defers to async writeback regardless of offset pattern — removes SEQ/RAND asymmetry. Tried, reverted once when it apparently regressed something, root-caused, and reapplied (`2713d92`→`c33a4cf`→`9e12711`). |
| Per-row lock/write granularity | one lock + one `pwrite()`/`pread()` per row → one lock per year-group + coalesced multi-row `pwrite()` runs | Both extremes (per-row, whole-span) were implemented and compared; whole-span won. Write coalescing detects contiguous runs so a fully sequential batch collapses to one syscall. |
| Aggregate scan I/O | fresh `fopen`+`mmap`+`munmap` per aggregate call → shared MRU-cached `GetOrMapFile` mapping (same cache every other read path uses) + `madvise(WILLNEED)` prefetch | Removes per-call mmap setup/teardown cost; prefetch avoids one page fault per touched page during a full-span scan. |
| Aggregate column extraction | full `RowData` parse (all columns decoded/allocated) → wire-level skip-parse of only the target column | Benchmarked ~40–54% faster (N=100/1k/10k); the old kernel and its A/B test harness were deleted after promotion. |
| Year-bucketing | `gmtime_r()` per row → closed-form civil-calendar math (`TimeStruct`) | Determinism (no TZ/locale dependency for on-disk addressing), resolution-awareness (fixes a MILLISECOND/MICROSECOND mis-bucketing correctness bug), and removes a libc calendar call from the hot path; further amortized by reusing the previous row's year-window across sorted-ascending batches. |
| Shared-state locking granularity | one global mutex per cache (mmap cache, fd cache, config cache) → sharded mutex arrays (64/4/16 shards respectively) | Cuts cross-DB/cross-file lock contention on cold-start bursts and steady-state hot paths; shard counts are individually tuned to each cache's miss cost and cap size, not uniform. |
| Request/response allocation | default heap allocator (per-submessage `new`) → per-worker-thread `google::protobuf::Arena`, `Reset()` each iteration | Converts per-row/per-column heap churn in wide batch/range responses into bump-pointer allocation off reused blocks; applied selectively (only to message trees with real nesting). |
| Per-call transient allocation | fresh `std::string`/`std::vector` per call (path formatting, serialize buffers, receive buffers) → `thread_local`/reused member buffers, grow-only | Removes a heap allocation from `CachedYearFilePath` (path string), `RowBuf`/`RunBuf`/`BufferIn` (serialize/read scratch), and the ZMQ receive-message vector — all reused across calls within a thread instead of reconstructed. |
| Wire dispatch | separate lightweight command-tag parse + full payload parse → single `Request` envelope `oneof`, `payload_case()` as the dispatch tag | One parse of the wire bytes total, not two. |
| Row-size validation | unchecked `SerializeToArray` (oversized rows silently truncated, corrupting the following row's slot) → `ByteSizeLong()` bound check, reject-and-report if oversized | Correctness fix; `ByteSizeLong()`'s result is also *reused* (not recomputed) for the actual serialize call, so the fix didn't add a second full-size computation. |
| Client warmup | `InfoRequest()` (directory scan) used as a connectivity probe → dedicated `Ping` RPC (empty round trip, no server-side `XStore` work) | Removes unnecessary server-side I/O from a pure liveness/handshake-forcing check. |
| Mmap/fd cache eviction | bare pointer/fd in cache, unconditional `munmap()`/`close()` on evict → `shared_ptr<MappedFile>`/`shared_ptr<int>` entries, deleter-deferred `munmap()`/`close()` | Fixed a use-after-unmap / use-after-close race: eviction could run while another thread was still mid-access on a pointer/fd read from the cache earlier, causing silent concurrent-insert data loss (reproduced under concurrent RND inserts once the working set exceeded cache capacity). Commit `d6b9ffe`. |
| Byte-range lock registry | one process-wide `shared_mutex` guarding the whole `path → FileRangeLock` map → 16-way sharded (`hash(path) % 16`) | `FileLockRegistry::Get()` runs on every single op call; one global mutex serialized lookups across *all* files, not just contending writers of the same file. Commit `d6b9ffe`. |
| DB-base-path / year-file-path formatting | fresh `DbBasePath()`/`fmt::format()` call per op, then a **single-entry** `thread_local` memo → per-thread hashmap memo (`CachedDbBasePath`/`CachedYearFilePath`) | The single-entry memo thrashed (missed nearly every call) under RND-pattern workloads bouncing between a handful of years in no particular order; a hashmap stays warm regardless of access order since a real year range is small. Commit `62ef571`. |
| `CachedDbBasePath` cache key | keyed by `dbName` alone → keyed by `(DataStoreDir, dbName)` | `dbName`-only keying let a later test's lookup for a reused `dbName` (e.g. `"TESTDB"`) silently return an earlier, already-torn-down test's path when the test suite `chdir()`s between scratch directories reusing the same `dbName`; harmless in production (one fixed `DataStoreDir` per process) but a real cross-directory aliasing bug in the test/embedding case. Commit `8c6c4fc`. |
| Aggregate scan dispatch | single-threaded `WalkYearSpan` over the whole span, always → `WalkYearSpanParallel`: narrow spans (< 4 years) unchanged, wide spans (≥ 4 years) striped across `min(#years, hardware_concurrency())` threads with per-thread partial state + sequential merge | Measured 5.08x speedup on wide multi-year aggregate queries with zero regression on narrow/single-year throughput. Reassociates Sum/Avg's floating-point addition (ULP-level difference from the sequential result) as an inherent, accepted tradeoff. Commit `8c6c4fc`. |
| `Batch`/`RangeInsert`/`Query`/`Delete` year-bucketing container | `std::map<year, vector<rowIndex>>` → flat `YearBucketMap` (`vector<pair<year, vector<rowIndex>>>`) with linear-scan `AppendToYearBucket` | A single request realistically touches only a handful of distinct years — a flat vector beats a tree map's per-key allocation/pointer-chasing at that small K. Commit `8c6c4fc`. |
| `BatchInsert`/`BatchQuery` DB-existence check | explicit `std::filesystem::is_directory()` stat before `GetOrLoadCfg` → dropped, relies on `GetOrLoadCfg`'s own stat-on-miss | `GetOrLoadCfg` already stats the `.CFG` file on a cache miss; the upfront check was a redundant `stat()` on every call regardless of cache state. Same fix already applied to the Unary ops earlier. Commit `8c6c4fc`. |
| `dbName` parameter passing | `std::string dbName` (by-value copy) on every public `XStore` method → `std::string_view dbName`, uppercased once into a reused `thread_local` buffer (`UpperCaseInto`) | Removes a `std::string` construction/copy at every call boundary plus the old copy-then-transform-in-place's second pass; one read-uppercase-write pass instead. Commit `8c6c4fc`. |
| `UnaryInsert` durability | OS page cache only, no explicit fsync barrier → real write-ahead log (CRC-framed records, per-shard adaptive group-commit writer threads, `ReplayWal` crash recovery) | Gives `UnaryInsert` a provable durability guarantee (SYNC) with group-commit-amortized cost, and a bounded-loss ASYNC mode, without needing an index for recovery (§4.12). |
| `BatchInsert`/`RangeInsert` durability | none beyond OS writeback → async data-fsync coalescer, deduplicated per touched fd | Simpler than a full WAL, sufficient for these operations' already-sequential/coalesced write pattern (§4.13); SYNC mode's guarantee is verified equivalent to the WAL's. |
| `BatchInsert`/`RangeInsert` durability (later) | async data-fsync coalescer → the same WAL as `UnaryInsert` (one record per (db, year) group, ASYNC/SYNC; BYPASS inline) | Closed the ASYNC crash-loss gap of the coalescer; supersedes the row above (§4.13 note, `docs/superpowers/plans/2026-09-08-async-batch-range-wal.md`). |
| `BatchQuery`/`RangeQuery` response construction | build full `RowData`/`FData` response object tree, then serialize | streamed, skip-copy multipart encoding straight from on-disk row bytes (§7.4) | Removed a permanent RSS floor under Arena `Reset()` for wide responses; server-side peak memory per query now bounded by one chunk (64MB), not the full result size. |
| Index crash-consistency | `.zmap`/`.catidx` never fsynced, no way to detect post-OS-crash inconsistency with the data; SIGTERM/SIGINT killed the process outright → per-file `dirty` header flag (fsynced once per file per session, cleared only after data + index `fdatasync`), dirty ⇒ rebuild at `InitDB`, plus `XStore::Shutdown()` and a `sigwait`-driven graceful server stop with WAL checkpoint | Closes the OS-crash/power-loss window for index-vs-data consistency (wrong pushdown results, bloom false negatives) at a measured fixed once-per-session cost (≈ −0.7 % BatchInsert at 1M rows, up to ≈ −8 % on ~0.15 s runs) and makes clean restarts cheap (0.15 s vs. 62 s rebuild after SIGKILL at 700k rows). Does not fix loss of acknowledged SYNC writes on power loss (closed afterwards by the WAL ring row below, §4.19) (§4.18). Commits `1f1e1959..a28af4cd`. |
| WAL durability past an OS crash / power loss | each shard overwritten from offset 0 by the next batch, data files never fsynced → append-only per-shard ring with LSNs (record v2), checkpointer that `fdatasync`s the dirty data files lazily and paced, then advances `checkpoint_lsn`; ≥ 1 MiB Batch/Range records bypass the ring (direct apply + one `fdatasync`); replay starts at the checkpoint | An acknowledged SYNC write now survives power loss (invariant: record in the live ring, or a data sync started after the write has completed) without a data fsync per commit. Measured (one noisy box, indicative): small records ≈ 0 %, medium (136 KB) −9 % on a 9 s run / +10 % on a 40 s run, large (2.7 MB) +6.6 % to ≈ +10 % vs. a baseline that gives no durability past an OS crash; Unary ASYNC −0.5 %; SIGTERM stop 1.43 s → 0.28 s; SIGKILL restart unchanged (~62–66 s, index rebuild, phase 2). Residual risks and test limits in §4.19. Commits `ff7728d3..ab41c638`. |

Several earlier cache-sharding rows above (mmap/fd/config/lock-registry) share one underlying rationale — a single global mutex per shared cache became a cross-DB/cross-file serialization point once every op called into it — with shard counts individually tuned per cache's own miss cost and cap size; see §4.4-§4.6 and §5.1 for the per-cache specifics rather than repeating them here.

### 10.2 In-repo performance micro-benchmarks

`tests/perf/XStorePerfTest.cpp` is deliberately **not** built on a benchmark library (no `google/benchmark` dependency) — each case is a plain timed loop (`std::chrono::steady_clock`) reported via `std::cout`, with only soft correctness assertions (no crash / no data loss), **no hard throughput/latency thresholds asserted** (explicitly documented: absolute numbers vary too much by machine to make a good CI gate; this suite exists to be read by a human doing perf work — e.g. comparing before/after a change — not to fail a build).

- Default op count: 200,000, overridable via `XSTORE_PERF_N` environment variable.
- Logging is forced to `spdlog::level::warn` in `SetUp()` — at 200k+ calls, per-call `[INFO]` stdout logging would dominate the timed loop and measure logging cost instead of `XStore`'s.
- Covers: Unary Insert/Query throughput (one row per call — "the shape of a single live write/read in production"), Batch Insert/Query throughput, and comparative kernels (`MinAggregateTypedVsGeneric_{Small,Medium,Large}` — the typed-double prototype vs. the generic skip-parse kernel, §6.4).
- Reported metrics per case: `rows`, `elapsed` (s), `throughput` (rows/sec), `avg_latency` (µs/row).

### 10.3 XBench — the external, multi-database distributed benchmark harness

**XBench** ("A distributed benchmarking framework for TSDB") is a sibling project from the same lab/author (found at `/home/ubuntu/XBench` in this environment; ships its own `README.md`/`instructions.md` and is *not* part of the XStore repository — it depends on XStore as a **git submodule**, `external/XStore` → `https://gitlab.com/lvn2007/XStore.git`, so it links against XStore's real client library rather than reimplementing wire logic). Its purpose is to drive **head-to-head comparative benchmarks** of XStore against other time-series-capable datastores under an identical workload generator and driver harness.

**Systems under test (per-DB adapter classes, uniform static-method interface):**

| Adapter | Wired into `main.cpp` dispatch tables? | Notes |
|---|---|---|
| `XStore_Adapter` | Yes | Wraps `XStore_Client` (the same C++ client described in §8.1). |
| `MongoDB_Adapter` | Yes | Only other adapter supporting arbitrary-timestamp-set `BatchQuery`. |
| `InfluxDB_Adapter` | Yes | `AggQuery` aggregate-type strings differ in case/spelling from XStore's (`"MIN"` vs Mongo's `"min"`; `AVG` maps to InfluxDB's `MEAN`). |
| `GraphiteDB_Adapter` | Yes | |
| `TimescaleDB_Adapter` | **No** — source exists (`TimescaleDB/TimescaleDB_Adapter.{h,cpp}`) but is not `#include`'d or wired into `main.cpp`'s dispatch maps; effectively unused/in-progress in this checkout. | |

`main.cpp` dispatches every operation through a `std::map<std::string, DispatchFn>` keyed by DB name, where `DispatchFn` is one function-pointer type shared by **every** adapter's `UnaryQuery`/`RangeQuery`/`BatchQuery`/`UnaryInsert`/`RangeInsert`/`BatchInsert`/`AggMin`/`AggMax`/`AggSum`/`AggAvg` methods — collapsing what would otherwise be a per-call-site 4-way if/else chain into one map lookup. Not every DB supports every operation shape: only XStore and MongoDB expose arbitrary (non-contiguous) timestamp-set `BatchQuery` (InfluxDB/Graphite fall through to an explicit "unsupported" warning); InfluxDB/MongoDB/Graphite have no wire-level distinction between a contiguous-range insert and an arbitrary-batch insert, so their "SEQ insert" path reuses the same `BatchInsert` adapter method XStore's dedicated `RangeInsert` RPC exists specifically to avoid.

**CLI surface** (`argparse`-based, `include/argparse.hpp`), four subcommands under a `bench` group — `bench query`, `bench agg`, `bench insert`, `bench proto` — sharing most flags: `-i/--ip_address`, `-p/--port_number`, `-d/--db_name {XSTORE,MONGODB,INFLUXDB,GRAPHITE}`, `-t/--thread_count`, `-e/--experiment_type {UNARY_SEQ,UNARY_RAND,BATCH_SEQ,BATCH_RAND}`, `-n/--n_iteration`, `-b/--batch_iteration` (batch/range group size, 0 for unary workloads), `-ia/--invoke_at` (a scheduled start time, letting multiple distributed client processes launch their runs synchronized rather than racing to start), `--debug`.

**Synthetic dataset generation (`DataManager`, using Apache Arrow/Parquet):**
- Each row's value cells are **deterministic MD5 hashes** of `(timestamp, columnIndex)` (`HashFromTimestamp` → `GetMD5String`), not sampled/real sensor values — chosen so generated data is exactly reproducible (any node can regenerate/verify the same dataset from the same time range/column count without shipping the raw values around) and so correctness can be checked by re-deriving the expected hash rather than storing an oracle copy.
- Parquet schema: column 0 is always `timestamp` (`INT64`/`UINT_64`); columns 1..N are `BYTE_ARRAY`/`UTF8` (the hash strings) — i.e. the benchmark's payload is string-typed, not numeric, for all non-timestamp columns (relevant caveat: XStore's own numeric aggregate kernels, §6.3, would find zero valid numeric columns against this exact synthetic schema — the aggregate workloads necessarily target a different, numeric-typed dataset variant, or exercise the aggregate RPCs' *code path/latency* rather than meaningful reduction results).
- `ChunkSize = 1000` rows is documented as the "optimal" Parquet row-group size used when writing.
- A separate **`ProtoBench`** module/CLI subcommand exists purely to measure raw protobuf serialize/deserialize cost (`entries × byteSize`, N iterations) in isolation from any database or network I/O — isolating wire-format marshaling overhead as its own variable from the end-to-end DB benchmarks.

**Workload parameter space** (from XBench's `README.md`, "To generate workload datasets"): thread counts **{1, 2, 4, 8, 16, 32}** per client node, across **8 client nodes**, for each of `UNARY_SEQ`/`UNARY_RAND`/`BATCH_SEQ`/`BATCH_RAND` query and insert workloads plus `AGG_MIN`/`AGG_MAX`/`AGG_SUM`/`AGG_AVG`. The sample commands use `-st 946684800 -et 1262303999` — **2000-01-01T00:00:00Z to 2009-12-31T23:59:59Z, a 10-year span** — and `-c 128` columns for data generation, which is precisely the `10Y_128-Cols_Experiments` corpus naming (§10.4): 10 years × 128 columns. Per-node workload files are offset-sharded via `-o` (row offset into the generated dataset) so each of the 8 nodes/32 threads works a disjoint slice.

**Multi-node orchestration (`run.sh`):** a `tmux` + `ssh`-based controller script that declares a `targetNodes` array (bash), opens one tmux window per target node, and broadcasts setup/build/data-generation/load/read/write commands to all nodes in parallel (`sendCMD` → `tmux send-keys` to every node's window), then collects each node's result files back to the controller (`scpRecvBenchResults`, one `Node-<idx>/` subdirectory per node) — the same node-indexed layout (`*_Node-0` .. `*_Node-7`) visible in XStore's `10Y_128-Cols_Experiments/` artifact directories. The script also documents the target install profile (Apache Arrow APT repo + `libparquet-dev` + `cmake g++ protobuf-compiler libprotobuf-dev libzmq3-dev` + `pandas`/`fastparquet` for the Python-side tooling).

## 11. Constraints, Assumptions, and Known Limitations

These are worth stating explicitly for a paper's "limitations/threats to validity" discussion:

- **`BaseDir` = process CWD.** `GetBaseDir()` returns `std::filesystem::current_path()` — the server assumes it is launched with its working directory set to the directory it lives in, with `DataStore/` as a direct child. No configuration flag overrides this.
- **2 GB protobuf response ceiling — a real, separate limitation, not something the streaming encoder solves.** `BatchQuery` and `RangeQuery` both explicitly reject requests whose estimated response size (`rowCount × rowLength`) exceeds 2,000,000,000 bytes — protobuf's own hard message-size ceiling — and this check runs *before* any chunk is built. The streamed multipart reply mechanism (§7.4) only bounds server-side peak memory for results *under* that ceiling; it cannot lift the ceiling itself, since the client still reassembles every chunk into one buffer before a single `ParseFromArray` call. There is no pagination/cursor mechanism across multiple request/response round trips today. Confirmed intentional (documented in-code), not an oversight.
- **Fixed row length per DB, set at `CreateDB` time, minimum 4 bytes.** A row cannot be resized later; a row whose serialized form exceeds the configured `rowLength` is rejected (not truncated, not auto-widened). The `xstore-viewer` tool's sizing-guide diagnostic (§8.3) helps catch a poorly-chosen `rowLength` after the fact.
- **No authentication/authorization/encryption on the ZeroMQ transport.** `tcp://` sockets bind and accept any client that can reach them; the only request-side safety check found is `RemoveDBFiles`' rejection of filenames containing `/` (defends against path traversal, e.g. `"../other.CFG"`, escaping the DB directory) and refusal to delete the DB's own `.CFG` file via that path. ZeroMQ's CURVE mechanism could add real encryption/auth at the cost of key management/distribution — worth prioritizing only if XStore ever runs on a shared/untrusted network segment.
- **Durability is WAL-level for `UnaryInsert`, `BatchInsert` and `RangeInsert`** (§4.12, §4.19; the fsync-coalescer design of §4.13 is superseded). **SYNC** inserts survive an OS crash or power loss: the WAL record stays in the shard's ring until a data-file `fdatasync` that started after the write has completed (records ≥ 1 MiB are `fdatasync`ed directly instead), subject to the residual risks in §4.19 — notably an unacknowledged write can in rare torn-write cases reappear after a crash, a record whose WAL sync failed can be replayed although its caller was told it failed, corruption mid-log discards the records behind it, and after a real writeback error the process must be restarted (the checkpointer is poisoned and writers eventually fail "overloaded"). **ASYNC** acknowledges before the WAL sync (a bounded crash-loss window) and its queued records are dropped at stop; **BYPASS** inserts and hole-punch deletes are not WAL-covered and rely on OS writeback (BYPASS rows are noted dirty and synced by a later checkpoint cycle, but no promise is made). A SYNC insert in flight at SIGTERM may be durable but unacknowledged. **Index consistency after OS crash / power loss is handled (Durability A, 2026-10, §4.18):** `.zmap`/`.catidx` carry a dirty flag and are rebuilt at startup if the previous session did not shut down cleanly; after SIGKILL or power loss this is a full-year rebuild (~62–66 s at 700k rows), because the index files are not yet stamped with the checkpoint LSN (phase 2, `TODO.md`).
- **The WAL is a fixed-size ring per shard, not a segmented log, and the writer applies to the data file synchronously rather than via a decoupled background materializer.** LSNs and checkpoint-based recovery exist since 2026-10 (§4.19); segmentation and a decoupled materializer remain open work in `TODO.md`, along with cross-process write coordination (below) and C++23/messaging-layer/storage-compression exploration.
- **Column identity is purely positional**, not named — reordering how a client populates `RowData.fieldData` changes column meaning; there is no schema registry mapping names to indices beyond what the client application itself tracks.
- **`CreateDB`'s time-resolution whitelist (`SECOND`/`MILLISECOND`/`MICROSECOND`) is narrower than what the time-math layer (`TimeStruct`/the `TimeUnit` enum) actually supports** (`NANOSECOND`/`MINUTE`/`HOUR`/`DAY` are implemented but not creatable via the public API) — an intentional (or at least current) restriction of the exposed surface, not a limitation of the underlying arithmetic.
- **`RangeInsert` assumes pre-sorted-ascending input** (documented, unchecked) — unlike `BatchInsert`, which sorts unconditionally. Passing unsorted data to `RangeInsert` is a caller contract violation, not a runtime-detected error.
- **Single-writer-per-slot correctness relies entirely on the in-process `FileRangeLock` registry** — it provides no protection against a second XStore *process* (not thread) writing the same files concurrently; the design assumes exactly one server process owns a given `DataStoreDir`. `FileRangeLock`'s own header comment documents this as an in-process-only design choice, not an oversight. Tracked in `TODO.md`.
- **`WalkYearSpanParallel`'s per-request thread cap has no cross-request coordination** (§6.4) — confirmed real: the ZMQ worker-thread count bounds concurrent *requests*, not *threads spawned per request*, so the two caps multiply rather than nest. Untested at the concurrency level that would expose it. A fix already exists in-repo (`XStorePreadPool::ParallelFor`, used by `BatchQuery` but not yet by the aggregate path) — tracked in `TODO.md`.
- **Parallel `Sum`/`AvgAggregate` results can differ by a few ULP from the sequential (narrow-span) result for the same data** (§6.4) — an inherent floating-point reassociation effect of combining per-year partial sums in a different order than a strict single continuous accumulation, not a bug.
- **Compiler warnings are globally suppressed** (`add_definitions(-w)` in `CMakeLists.txt`) and the build defaults to `-O3` Release with no assertions layer beyond what GoogleTest/normal C++ provides; AddressSanitizer/UBSan flags exist in `CMakeLists.txt` but are commented out by default (opt-in for debugging only). Re-enabling `-Wall -Wextra` is tracked in `TODO.md`.
- **XBench's synthetic non-timestamp columns are string-typed (MD5 hashes)**, chosen for deterministic reproducibility/verification rather than to model a realistic numeric sensor-data distribution — a paper citing throughput numbers from this corpus should note the payload is a synthetic worst/typical-case for serialization size and wire cost, not a claim about numeric-aggregate performance under that exact dataset (see §10.3).
- **XStore is today strictly single-node.** The `hash % N` striping described throughout §4-§5 is in-process lock/cache/WAL-queue striping only, never network partitioning — there is no cluster/membership/replication code, no node/shard/replica identity at any layer. A full distributed architecture (sharding, replication, failover, a competitive analysis against 15 SOTA systems, and estimated operation costs) is designed but not yet implemented — see `docs/XStore_Distributed_Architecture.md` and the corresponding `TODO.md` entry.

See the repository's `TODO.md` for the full, current list of tracked open work (effort-categorized), including items beyond what's called out inline above — C++23 migration, an alternative-messaging-layer research spike, and storage-level compression.

## 12. Build & Dependency Surface

- **Language/standard:** C++17 (`CMAKE_CXX_STANDARD 17`), compiled `-O3` in Release (the default build type if unspecified).
- **Required external packages:** Abseil (`absl`, transitively via Protobuf), Google Protocol Buffers (≥3.18.1, `optimize_for = SPEED`, `--experimental_allow_proto3_optional`), ZeroMQ C++ bindings (cppzmq, ≥4.8.1 per README; headers vendored under `include/Networking/`), POSIX Threads.
- **Vendored (bundled in-tree, not fetched):** spdlog (+ bundled fmt) under `third_party/spdlog/` — the large majority of the graphify-derived node/edge count for this repository is this vendored logging/formatting library, not XStore's own logic; ZeroMQ C++ header bindings (`zmq.hpp`, `zmq_addon.hpp`, `zhelpers.hpp`) live under `third_party/` (server copy) and are duplicated under `client_src/Cpp/third_party/` (client copy, kept self-contained within `client_src/Cpp/` so the client library has no dependency outside its own directory and can be copied out standalone).
- **Fetched at configure time:** GoogleTest v1.17.0 via CMake `FetchContent` (only if `XSTORE_BUILD_TESTS`, default `ON`); RE2 `2025-11-05` via CMake `FetchContent` (`XSTORE_FETCH_RE2`, default `ON` — OFF uses a system RE2 via pkg-config instead), built against protobuf's already-fetched Abseil, needs CMake ≥ 3.22 (otherwise REGEX mode is disabled). **jemalloc 5.4.0** (`XSTORE_USE_JEMALLOC`, default `ON`): release tarball pinned by SHA256 (`200776fa…4f1d`), built once at configure time into `_deps/jemalloc-install` (same `FetchContent_Populate` + `execute_process` pattern as libsodium), linked **statically into the `XStore` server and `xstore_perf_tests` only** — never `xstore_core`, the client library, or the unit/network test binaries (`XStoreMemoryTest` relies on glibc `mallinfo2`). The archive is linked with `-Wl,--whole-archive`: XStore's own objects never reference `malloc` directly (allocation goes through `operator new` in `libstdc++.so`), so a plain static link silently leaves glibc as the allocator. The executable then defines and exports `malloc`/`free`, which the shared protobuf/zmq/libstdc++ resolve to. Compiled-in tuning: `src/XStore_Alloc/jemalloc_conf.cpp` sets `malloc_conf = "background_thread:true,thp:always"` when **`XSTORE_JEMALLOC_THP`** is ON (default), or `"background_thread:true"` when OFF; runtime `MALLOC_CONF` still overrides. THP needs the host's `/sys/kernel/mm/transparent_hugepage/enabled` to be `madvise` (jemalloc then requests huge pages itself) or `always`; with `never` the option has no effect. Automatically disabled when `-fsanitize` is in the compile/link flags. Check a build: `nm -D build/XStore | grep -w malloc` shows `T` (jemalloc) vs `U` (glibc); `MALLOC_CONF=stats_print:true ./build/XStore --help` prints jemalloc's stats.
- **Build targets:** `XStore` (server executable), optional `client_src/Cpp` subdirectory (`XSTORE_BUILD_CLIENT`, default `ON`), optional `tests` subdirectory (`XSTORE_BUILD_TESTS`, default `ON`).
- **Large-file support** explicitly enabled (`_LARGEFILE_SOURCE`, `_LARGE_FILES`, `_FILE_OFFSET_BITS=64`) — expected given year-files can be large, fixed-width, and pre-`ftruncate`d to full-year capacity up front.
- **CI** (`.gitlab-ci.ymll`, GitLab CI over LXC-restored runners): stages are Initialize (LXC snapshot restore) → OS Configuration (apt update/upgrade, install `build-essential cmake g++ protobuf-compiler libzmq3-dev libzstd-dev`) → Build (server, then client) → Test → Cleanup.
- **XBench's own dependency surface** (separate build, §10.3): additionally requires Apache Arrow + `libparquet-dev` (via Apache's APT source) for its `DataManager`'s Parquet I/O, `argparse.hpp` (vendored header-only CLI parser), and driver-side database clients for whichever comparison systems are under test (MongoDB, InfluxDB, Graphite, and — unwired — TimescaleDB).

## 13. Reference: RPC Surface Summary

| RPC | Request → Response | Notes |
|---|---|---|
| `PING` | `ReqCMD` → `Ping_REP{}` | No `XStore` work; pure round-trip for handshake/liveness. |
| `INFO` | `ReqCMD` → `SysInfo_REP` | Full DataStore directory scan; per-DB file listing + allocated-byte accounting. |
| `CREATEDB` | `CreateDB_REQ{dbName,timeResolution,rowLength}` → `CreateDB_REP` | `rowLength ≥ 4`; resolution ∈ {SECOND,MILLISECOND,MICROSECOND}; idempotency: fails if DB dir already exists. |
| `REMOVEDB` | `RemoveDB_REQ{dbName}` → `RemoveDB_REP` | Recursive directory removal + cache eviction (config, mmap, fd) under that prefix. |
| `REMOVEDBFILES` | `RemoveDBFiles_REQ{dbName, [fileName]}` → `RemoveDBFiles_REP{[status]}` | Per-file status; rejects path-separator-containing names and the DB's own `.CFG`. |
| `UNARYINSERT` / `UNARYQUERY` / `UNARYDELETE` | single `(timestamp, [RowData])`; insert takes `durabilityMode` (ASYNC default/SYNC/BYPASS) | Point ops; insert routes through the WAL (§4.12), query via `pread`, delete via `fallocate` hole-punch. |
| `BATCHINSERT` / `BATCHQUERY` / `BATCHDELETE` | `repeated (timestamp[, RowData])`, arbitrary (non-contiguous) timestamp set; insert takes `durabilityMode` | Sorted (parallel above 10k elements), year-bucketed, whole-span-locked, run-coalesced writes; insert durability via the WAL ring, one record per (db, year) group, or the direct path for records ≥ 1 MiB (§4.12, §4.19). `BatchQuery` omits holes from the response entirely, replies streamed (§7.4). |
| `RANGEINSERT` / `RANGEQUERY` / `RANGEDELETE` | contiguous `[startTime, endTime]` (insert takes explicit per-row data, assumed pre-sorted); insert takes `durabilityMode` | `RangeQuery` returns **every** timestamp in range including holes (as empty-field entries) — the opposite convention from `BatchQuery`; replies streamed (§7.4). 2 GB total-result ceiling enforced (§11), independent of streaming. Insert durability via the WAL ring or the direct path (§4.12, §4.19). |
| `MIN` / `MAX` / `SUM` / `AVG` | `(startTime, endTime, dbName, columnIdx)` → single `FData`/`double` + status | Single-column reduction over `[start,end]`, walked year-file-by-year-file via `WalkYearSpan`/`WalkYearSpanParallel` for wide spans (§6.4); non-numeric/holed rows excluded from the reduction, not treated as zero. |
